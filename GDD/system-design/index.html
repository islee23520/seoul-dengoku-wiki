정의된 디자인을 어떤 구조로 만드는가

《잔선: 서울》은 붕괴 이후 지하철망을 영토로 쓰는 인물 중심 4X+RPG다. 규칙(세계가 어떻게 바뀌는지)은 Unity 없이 Janseon.Core에 두고, 화면·씬·입력은 Janseon.Foundation이 명령을 보낼 뿐이다. 코어 루프는 POC에서 출발했고 현재 이동 그래프는 OSM 작업 카탈로그를 읽는다. 지역 전체의 면적·시설·내용은 별도의 서울 지역 총람에서 확인한다. 16국 시뮬레이션과 파일 저장은 아직 구현 범위 밖이다.

한 장 지도

플레이어가 하는 일(거점 → 원정 → 조우 → 전투/교섭 → 정산 → 복귀)은 캠페인 명령이 되고, 화면은 그 명령을 보낼 뿐 상태를 직접 고치지 않는다.

의존 방향은 Foundation → Core 한 쪽이다. Core는 Unity·VContainer를 모른다. Game/Assets/Janseon/AGENTS.md, Core/Core.asmdef.

조립 — 누가 무엇을 소유하나

저장소 어셈블리는 네 개다. 전투는 별도 어셈블리가 아니라 Core 안의 Battle.Contracts·Battle.Sim이다.

엔진 없는 규칙이다. 전역 가변 상태를 두지 않는다. 화면이 상태를 직접 고치지 않고 명령을 보내면, 결과는 사건 원장에 남는다. 파일: Game/Assets/Janseon/Core/DeterministicCore.cs, RouteDomain.cs, CampaignDomain.cs, SettlementDomain.cs, Core/Battle/.
규칙이 아니라 에디터에서 찍는 데이터다. Repository 인터페이스와 DTO는 Core 쪽에 두고, 파일·Unity API 구현만 어댑터가 갖는다. 근거: docs/game-logic/Unity-Architecture.md 영역별 책임 표, Unity-System-Design.md Repository 경계.
App scope는 Bootstrap만 소유한다. 콘텐츠 씬은 배타적 child scope다. 세션을 Core에 붙이는 곳은 Foundation/UI/PocCoreLoopController.cs. 전환은 Foundation/AppFlow/ApplicationFlowCoordinator.cs만 승인한다. SceneManager.LoadScene*는 scene loader adapter만 호출한다.
런타임 슬롯 카탈로그는 있다. Home에 적혀 있다: 생성 아트 슬롯은 아직 런타임 화면에 연결되지 않았다. 초안은 Art/Staging/에 두고 런타임이 읽지 않는다. 파일: Foundation/Art/RuntimeSlotCatalog.cs.
시스템 설계 문서의 목표 조립도(Janseon.App / Presentation / Sim)는 첫 증분의 그림이다. 지금 코드는 Foundation 한 모듈에서 시작해, 두 번째 책임과 호출자가 생기기 전에는 빈 어셈블리를 만들지 않는다. Unity-System-Design.md 「모듈 의존성」.

씬과 앱 FSM

플레이 가능 빌드 순서는 Bootstrap → MainTitle → Foundation이다. Bootstrap만 프로세스 root다. 콘텐츠 화면은 동시에 둘을 열지 않는다.

MainTitle.unity / Foundation.unity 카메라, 조명, presenter, child LifetimeScope 전역 앱 상태, 저장 구현, 다른 씬 객체

상태를 누르면 코드 전이표 기준 허용 트리거가 나온다.
  • 표에 없는 전이는 Rejected(IllegalTransition) — 상태·씬·저장을 바꾸지 않는다.
  • 전환 중 두 번째 요청은 Rejected(Busy) — 두 번째 load를 시작하지 않는다.
  • 이미 도착한 같은 목적지 요청은 저장된 receipt만 돌려준다.
  • ready signal 전에는 안정 상태를 commit하지 않는다. 고정 sleep 금지.
  • 제품 코드에서 Container.Resolve 금지. constructor injection.
  • mutable static Instance/Current 금지. Singleton은 “현재 VContainer scope의 단일 인스턴스”다.

월드맵 — 노선 그래프, 층, 격자

세계 진실은 역과 연결의 그래프다. 화면은 지금 필요한 노선만 보여 주고, 역을 고르면 같은 그래프에서 4방향 격자를 펼친다. 대각 입력은 행동을 쓰지 않고 거절한다.

세 역 그래프

서울 지역 총람 — 경계와 지역 내용

25개 구 · 427개 동의 지도와 지역별 내용 열기

2026-07-01 행정동 경계와 2026-09-04 OSM 스냅샷을 분리해 사용한다. 역 없는 동과 이름 없는 시설도 자료 원장에 남긴다. 지역 저작 데이터와 Unity 내부 공간의 구현 상태는 구별한다.

  • 선택 경계는 427개 동의 합집합이며 옛 KOSTAT 2013 경계와의 차이를 기록한다. 공식 최신 경계 인증은 아니다.
  • 기존 334역은 이름 기반 작업 목록으로 중복·고립·분류 오류가 있어 현실 전수로 사용하지 않는다. 새 총람은 원자료 객체 ID와 위치를 보존한다.
  • 시설의 실제 위치·용도와 붕괴 뒤 가동·소유·지역 사건은 각각 관측 자료와 창작 설정으로 구분한다.
  • 조립 순서와 입장 시 층·격자·시설 슬롯은 World-Map-Construction.md, Seoul-Station-Catalog.md, Station-Interior-Construction.md.
  • 조우 정산 API는 대합실을 짓지 않는다.

도메인 API

도메인 파일은 타입을 파일당 하나로 쪼개지 않는다. ID·명령·상태·거절·API를 한 파일에 둔다.

CoreApi · PurposeRng

POC에 있음

정수 Tick만 세계 시간이다. 벽시계·프레임·instance id·GetHashCode는 규칙 입력이 아니다.

  • RNG 목적: World, Battle, Encounter, Loot. 한 스트림을 소비해도 다른 커서는 안 움직인다.
  • Peek은 상태를 바꾸지 않는다. Consume만 해당 목적을 전진한다.
  • 같은 요청 ID + 같은 payload → 기존 receipt. 같은 ID + 다른 payload → conflict.

전투장 — 같은 격자, 다른 시계

카메라를 바꾸지 않는다. 탐색에 쓰던 고정 직교 아이소(yaw 45°, pitch 35.264°)와 1.5m 칸 위에서 시간만 30Hz 틱으로 흐른다. 병사 한 명을 한 칸씩 옮기는 턴제가 아니다.

한 판이 시작될 때

BattleContext 동결

캠페인이 넘기는 묶음: 캠페인 ID, 역(StationId), 세계 시드, 틱, 물자, 평판, 규칙 버전, 조우 identity, 시작 HP. 여기서 BattleId와 컨텍스트 해시를 만든다. 전투가 시작된 뒤 바깥 세계를 다시 읽지 않는다.

  • 기본 전장 ArenaState: 가로 12, 세로 8. 지형 Heightmap이 있으면 그 너비·높이를 쓴다. Core에 전장 원형 enum은 없다.
  • 진형 격자 계약: 행 3, 열 3. 지휘 반경 3칸.
  • 역할 표(근위·돌격·궁수) HP 30/20/14, 위력 4/6/3, 사거리 1/1/3.
  • 규칙 버전 rtfc-owner-cards-v2. 예전 ownerless replay는 변환하지 않고 거절.

플레이어가 하는 일 / 안 하는 일

규칙 있음, 분대 명령 미완

  • 하는 일: 전투 전 전열·후열·측면과 4방향 정면. 전투 중 인물 카드 (OwnerUnitId, CardId)와 거점 카드 최대 2장. 재충전 300~900틱. 덱 구축·무작위 드로우 없음.
  • 안 하는 일: 개별 병사 한 칸 조작. UI Transform으로 Core 이동을 대신하기.
  • 시계: 30틱/초, 칸 이동 10틱, 공격 쿨 30틱, 한 판 상한 9000틱. D1 드라이버만 프레임당 최대 4스텝.
  • 사기 기본 60, 경고 40, 회복 상한 80. 항복은 사기 20 이하·지휘관 HP 50% 이하·퇴로가 모두 참일 때만. 지휘관 타일 점거는 퇴로 차단이 아니다.

문서의 전장 원형(작은 역사, 환승역, 종착역, 터널, 지상 폐허, 차량기지, 한강 횡단)은 설계다. 런타임은 12×8 또는 Heightmap 크기만 연다.

설계만 분대 Move/Attack/SetFacing 완료 검증, 0..4 집계 생존수 표시. 정산은 논리 UnitId와 남은 HP만 본다.

세이브와 결정론 — 계약은 있고 파일 저장은 없다

이미 지키는 것

해시·원장·RNG

  • 같은 seed + canonical command log → 같은 state/ledger hash.
  • 모든 상태 변화는 원인 ID, 세계 시간, 전후 요약 해시를 원장에 남긴다.
  • 씬 load 완료 시점은 도메인 결과에 영향을 주지 않는다.
  • 동일 seed 재현과 중복 정산 거부를 batchmode PlayMode에서 검증했다고 Home에 적혀 있다.

아직 만들지 않은 것

파일 저장 비목표

  • ICampaignRepository는 설계 계약이다. Foundation 첫 증분은 구현하지 않고 경계 게이트만 둔다.
  • 저장 envelope(판본, seed, tick, RNG 커서, pending battle, checksum)은 문서에만 있다.
  • temp 작성 → flush → 재읽기 → backup → 원자 교체. 깨진 세이브는 조용히 복구하지 않는다.
  • ToDo.md 비목표: 파일 저장/불러오기.

구조를 늘릴 때 지키는 규칙

  1. 새 게임 규칙은 Core에 순수 함수/API로 넣는다. Unity 타입을 넣지 않는다.
