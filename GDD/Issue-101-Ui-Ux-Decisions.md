# #101 UI/UX 화면 계약 — 확정 결정 1–9

- 상태: #101 의사결정 1–9 확정. 후속 전투 목표 변경은 아래 주석으로 구별
- 기록일: 2026-09-16, 2026-09-17 보완; 2026-09-19 전투 목표 변경 주석
- 근거 이슈: [#101](https://github.com/islee23520/seoul-kenshi/issues/101)
- 적용 범위: HTML 목업의 화면 구조·정보 표현·향후 Unity 요소 이름
- 비적용 범위: Unity 구현, 서버·네트워크, 수치 공식, 데이터 저장

이 문서는 #101을 진행하기 위해 소유자와 합의한 화면 계약을 기록합니다.
검토 과정의 생성 이미지는 화면 구조와 정보 우선순위를 판단하기 위한 예시로만
사용했습니다. [Intent](../Intent.md) 결정 8의 이미지 생성 금지와 UI 제3 표면
계약에 따라 해당 이미지를 저장소 아트 또는 Unity 실행 증거로 채택하지 않습니다. 실제 목업은
[UI가 코드로 들어오는 길](Ui-Implementation-Pipeline.md)과
[온라인 사용자 여정](Online-User-Journey.md)을 따라 별도로 갱신합니다.

## 결정 1 — 독립적으로 판단할 화면을 분리한다

플레이어 여정에서 독립적으로 판단해야 하는 화면은 아래 12면입니다. 최초
열 면 합의 이후 `출격 인원 선택`과 `전투 전 진형 편집`이 서로 다른 행위임을
확인해 각각 분리했습니다. 기존 HTML의 `배치 준비`는 출격 인원 선택을
묘사하지만 조우 뒤에 놓여 있어 제작 단계에서 거점 준비 뒤로 옮겨야 합니다.

| 순서 | 상위 화면 | 화면이 답해야 하는 질문 |
| --- | --- | --- |
| 1 | 캐릭터 생성·착생 | 나는 세계의 어떤 인물로 시작하는가? |
| 2 | 시작 프리셋 | 어떤 결핍과 장기 규칙을 감수하는가? |
| 3 | 세계 인물 모집 | 누구를 만나고 동행을 제안할 수 있는가? |
| 4 | 거점 허브 | 현재 거점에서 누구와 무엇을 할 수 있는가? |
| 5 | 캐릭터 대화 | 상대와의 관계 및 선택 결과가 어떻게 달라지는가? |
| 6 | 출격 인원 선택 | 로스터에서 누가 이번 원정에 참가하는가? |
| 7 | 전략 노선도 | 알고 있는 세계에서 어디로 향할 수 있는가? |
| 8 | 역간 여행 | 목적지까지 어떤 경로·비용·위험을 감수하는가? |
| 9 | 조우 | 마주친 상황에 어떻게 대응하는가? |
| 10 | 전투 전 진형 편집 | 참가 인원을 어디에 어떻게 배치하는가? |
| 11 | 전투 | 부대 명령과 전투 일시정지로 교전을 어떻게 지휘하는가? |
| 12 | 정산 | 선택과 전투가 인물 및 세계에 무엇을 남겼는가? |

계정·로그인은 상위 화면에 추가하지 않고 `열쇠` 자리만 둡니다. 무작위/커스텀은
캐릭터 생성·착생 화면의 내부 갈래입니다. 출격 인원 선택은 평상시 거점 준비,
진형 편집은 조우 후 교전 전의 화면이며, 둘 다 전투 중 화면이 아닙니다.
실시간/일시정지는 전투 화면의 내부 상태입니다. 2026-09-19 결정 11 이후 목표 전투는 카드가 아닌 부대·진형 지휘입니다. 기존 카드 UI와 수치는 POC 기록으로만 남기며 목표 화면에 승격하지 않습니다. 카메라·일시정지 세부 동작은 소유자 명시 결정이 아니라 질문 만료 뒤 채택한 설계 기본값입니다. [실시간 부대 지휘 전투](rules/Realtime-Formation-Card-Battle.md)를 따릅니다. 기존 UI 파이프라인의 8칸
보드와 그 요소 이름은 이 12면의 개수와 별개로 유지합니다.

## 결정 2 — 상태와 장소는 지속하고, 상황은 맥락이 생길 때만 연다

- **상태**: 플레이어 인물의 현재 상태를 평상시에도 지속적으로 보여줍니다.
- **장소**: 현재 위치를 평상시에도 지속적으로 보여줍니다.
- **상황**: 사건이 예고되거나 실제로 직면했을 때만 추가로 보여줍니다.
- **화면 맥락**: 평상시와 예고 상태를 전투 화면으로 표현하지 않습니다. 예시 화면은
  사용자가 다음 행동을 판단할 수 있도록 해당 맥락의 실제 플레이 시점을 사용합니다.

따라서 평상시에는 상태·장소만 조용히 유지하고, 예고 시에는 기존 플레이 화면 위에
주의와 남은 시간을 추가하며, 직면 시에는 선택 가능한 상황 패널을 엽니다. 실제 상황이
전투일 때에만 전투 화면과 전투 HUD를 사용합니다.

## 결정 3 — 사실은 활동으로 얻고, 예측은 능력으로 넓힌다

전략 노선도와 거점 정보는 전지적 세계 지도가 아닙니다.

- 플레이어가 직접 알게 된 역과 노선만 정확한 사실로 표시합니다.
- 미발견 영역에는 정확한 역·노선·세력 정보를 제공하지 않습니다.
- 직접 활동하여 수집한 정보는 확인된 사실로 승격합니다.
- 전언 등 간접 정보는 사실과 구별되는 소문으로 표시합니다.
- 예측 가능한 범위와 정확도는 플레이어의 레벨 및 관련 능력치에 따라 달라집니다.
- 예측은 확인된 사실처럼 보이지 않도록 범위·가능성·신뢰도를 함께 표시합니다.

화면상 최소 정보 상태는 `미발견`, `소문`, `직접 확인`입니다. 정보 출처와 공유 범위의
화면 원칙은 결정 4에서 정하고, 정확한 노후화 기준과 능력치별 계산식, 저장,
동기화, 서버 권위는 #101의 HTML 화면 계약이 아니라 후속 구현 이슈의 범위입니다.

## 결정 4 — 관계 신뢰와 정보의 신뢰성을 분리한다

인물 사이의 신뢰는 방향성이 있습니다. `동료 → 나`와 `나 → 동료`를 하나의
상호 신뢰 수치로 합치지 않습니다. 관계 패널은 인물의 태도와 그 근거를 보여주고,
플레이어의 감정을 자동 점수로 단정하지 않습니다.

정보 카드는 관계 패널과 별도로 원출처, 전달자, 입수·확인 시점, 검증 상태,
독립 출처를 보여줍니다. `오래됨`과 `상충함`은 검증 단계가 아니라 추가 표지입니다.
친밀한 동료가 전달해도 소문은 소문이고, 관계가 나빠도 직접 확인한 사실은 사실입니다.

- 함께 목격한 사실과 공동 임무에 필요한 작전 정보는 파티에 공유합니다.
- 동료가 따로 얻은 정보와 개인 비밀은 관계, 동기, 맹세, 공포, 소속에 따라
  공개·보류·부분 공개가 달라질 수 있습니다.
- 관계는 **무엇을 언제 얼마나 말할지**, 정보의 출처·시간·검증은 **내용을
  얼마나 믿을지** 판단하는 데 사용합니다.
- 화면은 이 두 판단을 별도 위치와 표지로 표현합니다.

정확한 노후화 기간, 관계 단계의 내부 값, 정보 공유 판정식은 후속 시스템 설계에서
정합니다. 의사결정용 예시는 평상시 거점 대화 시점이며 전투 화면이 아닙니다.

## 결정 5 — 공유 세계 원장은 인물이 아는 범위로 투영한다

권위 있는 세계 원장은 하나지만 플레이어 화면은 원장 전체를 방송하지 않습니다.
현재 인물이 직접 경험했거나, 알려진 장소·노선·관계 인물을 통해 입수한 사건을
맥락별로 보여줍니다.

- 거점 게시판: 현재 거점과 알려진 주변 노선의 관련 소식.
- 전략 노선도: 이미 아는 역·노선에 연결되는 변화 표식.
- 인물 기록: 해당 인물과 관련되어 플레이어에게 전달된 사건.
- 필요할 때 여는 세계 기록: 내가 알게 된 사건의 출처·시점·검증 상태.

다른 파티의 전투는 과정 전체가 아니라 알려진 최종 결과만 짧게 전달합니다.
모르는 지역의 사건, 정체를 모르는 행위자의 이름, 숨겨진 사건의 존재나 개수를
미리 누설하지 않습니다. 사실과 소문은 결정 3·4의 표지를 그대로 사용합니다.
상시 뉴스 티커 대신 관련 화면에 조용한 변경 표시를 둡니다.

## 결정 6 — 착생과 프리셋의 충돌은 확정 전에 예고한다

착생에서 정한 혈연·소속이 프리셋의 장기 규칙과 충돌하면 착생이 우선한다는
[기존 계약](Online-User-Journey.md)은 바꾸지 않습니다.
시작 프리셋 선택 화면에는 `적용 결과 미리보기`를 두고, 착생에서 유지되는 값,
프리셋으로 적용되는 규칙, 충돌하여 적용되지 않는 규칙을 구분합니다. 충돌 항목만
강조하고 확정 전에 확인할 수 있게 합니다. 새로운 상위 화면은 추가하지 않습니다.

## 결정 7 — 조종 주체를 숨기되 선점 인물도 포섭할 수 있다

NPC인지 다른 플레이어가 조종 중인지 인물 카드·모집 화면·일반 대화에서
구분할 수 없게 합니다. `플레이어`, `NPC`, `점유 중`, 접속 상태, 계정 식별자 같은
메타 표지를 노출하지 않습니다. 선점된 세계 인물도 포섭 대상에서 자동 제외하지
않으며 포섭을 제안할 수 있습니다.

포섭은 상대 인물과의 관계 또는 소속을 맺는 행위이지, 그 인물의 조종권을
가져오는 행위가 아닙니다. 한 `personId`에 살아 있는 계정 하나만 연결된다는
[점유 계약](Online-User-Journey.md)은 유지합니다.
상대의 자율적 수락 없이 조종권·파티 지휘권을 옮기는 것으로 해석하지 않습니다.

화면은 같은 `포섭 제안` 진입점을 제공하되, 결과·응답 시간·거절 문구가
조종 주체를 곧바로 폭로하지 않도록 설계해야 합니다. 실제 수락 절차,
오프라인 상태의 처리, 공동 파티의 지휘·전투 권한은 후속 시스템 결정으로 남깁니다.

## 결정 8 — 죽음·계승은 네 개의 보조 목업으로 포함한다

#101의 12면과 기존 8칸 보드를 늘리지 않고 다음 네 맥락을 보조 목업으로
설계합니다. 사망은 전투 밖에서도 발생하므로 전투 정산 화면에만 묶지 않습니다.

1. 생전 후계 지정: 지정 인물의 현재 유효 여부와 예상 작위·자산·분쟁을 구분.
2. 사망 후 유효한 후계자: 같은 월드에서 그 인물로 플레이를 이어가되, 작위와
   자산은 별도 규칙으로 판정하고 망자의 지식을 자동으로 옮기지 않음.
3. 사망 후 유효한 후계자 없음: 해당 플레이 게임오버. 이후 착생은 새 월드에서
   새 인물로 시작하며 망자의 정보·자산을 승계하지 않음.
4. 계정 아카이브: 두 결과 모두 망자의 기록을 지속 열람. 열람은 새 인물의
   게임 내 지식으로 취급하지 않음.

다른 플레이어가 조종 중인 인물은 포섭 제안 대상일 수 있지만 지정 후계자는
될 수 없습니다. 지정 후계자는 자신과 다른 살아 있는 인물이어야 하며,
사망 순간에도 다른 계정에 바인드되지 않아야 합니다. 사전 유효성은 경고와
재지정 기회만 제공하며 최종 판정은 사망 순간에 합니다. 유효한 지정 후계자가
그 순간 없으면 게임오버입니다.

플레이 조종권의 승계와 작위별 정치적 승계는 별개입니다. 작위는 해당 지역의
관습·교리·인준 및 경쟁 후보를 따릅니다. 작위가 없으면 작위 승계 판정도
없습니다. 개인 소유물·직위 재산·조직 재산 및 계약상 권리는 구분하며,
정확한 배분식은 후속 시스템 설계에서 정합니다. 새 월드의 생성·참가 방식도
후속 온라인 설계의 과제이고 #101 화면 설계가 서버 정책을 확정하지 않습니다.
정본의 구체 변경은 [온라인 사용자 여정](Online-User-Journey.md)에 함께 기록합니다.

## 결정 9 — 목업과 Unity가 공유할 안정 요소 이름

9번은 화면 제목만 짓는 일이 아닙니다. 조작 가능하거나 상태에 따라 바뀌고
테스트할 요소에 목업에서 기계적 이름을 부여하고, 이후 Unity
`UiElementNames`가 같은 이름을 사용하도록 하는 계약입니다. 기존
`deploy-panel`, `formation-edit`, `battle-dock`, `settlement-panel` 등은
개명하지 않습니다. 새 이름의 목록과 동적 ID 패턴은 [Design §11](../Design.md)에
기록합니다. HTML 목업은 이 계약을 적용해야 하며, Unity 코드 반영은 후속
구현 이슈입니다.

UI 표시 상태 값은 요소 이름과 구분합니다. `situation`은
`hidden|forecast|active`, `knowledge`는 `unknown|rumour|confirmed|inferred`,
`heir-validity`는 `unassigned|eligible-now|invalid-now`를 씁니다.
`eligible-now`는 사전 안내이지 사망 순간의 최종 판정이 아닙니다.
포섭 화면에는 NPC/다른 플레이어 구분을 나타내는 요소나 상태 이름을 두지 않습니다.

## 후속 구현 이슈로 넘길 것

- 역·노선 발견 상태 및 정보 출처 저장
- 정보 노후화와 갱신 규칙
- 능력치별 예측 범위·정확도·신뢰도 계산
- 파티 및 다른 플레이어 간 정보 공유와 서버 동기화
- 포섭 제안의 수락·거절·오프라인 처리와 공동 파티 권한
- 확정된 HTML 목업의 Unity uGUI·TMP 구현
