## Second-expedition LastSettledResult guard

The potentially stale controller `LastSettledResult` is retained across Return/Depart, but it is **not eligible** for the first OnSettle branch on a new expedition: `CampaignDomain.cs:327` explicitly sets `next.SettlementApplied = false`. The executable assertion at `StateProbe.cs:146` checks this after actual retained-assembly Depart, along with reset Choice/Consequence/SettledResultId/LastReceiptHash and retained RNG. `PocCoreLoopController.cs:294` requires both SettlementApplied and LastSettledResult; `:302-307` then constructs a new FromNonCombat result from the current second encounter. The probe observed negotiation result `result-22598d95f05d6605` at tick6 followed by bypass result `result-b35c5a9d4d290ba6` at tick13, totals 95/3 -> 93/2. A deliberate direct retry of the old negotiation payload on the new expedition returned its old receipt and changed nothing (`probe-results.log:9-14`). Thus the domain reset is executed and the controller guard is source-traced; the controller itself is not falsely claimed executed.

Simulation continuity also does not imply tactical agency: `PocCoreLoopController.cs:259-277` selects the first successful deterministic candidate, with candidates generated at `:437-553`, including the enemy's actions. `Design.md:191` accepts this POC limitation. The probe's controlled legal-command outcomes test simulation/result propagation, not player-selected move/attack controls.

## Trust-boundary findings (reproduced, not live exploit claims)

1. **Cross-campaign AttachPendingBattle accepts a real foreign context.** `CampaignDomain.cs:217-267` checks stage/choice/pending status, not `context.CampaignId == state.CampaignId`. Public APIs generated a legitimate context for `campaign-A`; attaching to `campaign-B` returned CampaignState with PendingBattle.CampaignId `campaign-A`. See `BOUNDARY|crossCampaignAttach` output. The actual controller `:224-236` immediately uses the context generated from its own current campaign, so ordinary UI handoff is source-correct. A future repository/message adapter must establish ownership before relying on this API.
2. **Noncombat Apply does not bind first result to the receiver's choice/encounter identity.** `SettlementDomain.cs:369-397` validates noncombat stage/shape but does not compare outcome to locked choice or recompute expected result provenance. A real FromNonCombat bypass payload from another campaign applied to a receiver locked to Negotiate: SettlementSuccess, receiver becomes Bypass, resources 98, reputation -1 rather than negotiation's 95/+3. See `BOUNDARY|foreignNoncombatResult`. The current controller constructs FromNonCombat from its own current state at `:302-307`, so not a demonstrated UI misroute. Exact-once protects an already-recorded payload; it does not authenticate the first supplied payload.

These are domain caller-trust limitations relevant to future wider integration, not grounds to mislabel intentionally excluded save/world systems as current-module regressions.
