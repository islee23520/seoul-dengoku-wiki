# Contributing

Read [WORLD_BUILDING_GUIDE.md](WORLD_BUILDING_GUIDE.md) in full before editing, then the applicable area instructions. PostgreSQL `wiki` is the operational authoring authority; private editorial/Soul records remain within `wiki_private`. Edit supported typed heads through `scripts/cast-sqlite/document-cli.mjs`, not generated output or recreated JSON source files. Edits create drafts, not inherited approval. The tracked canonical SQLite has been removed; an explicitly supplied external SQLite is for migration/comparison only, never normal authoring or runtime fallback.

Public narrative is Korean-only; simultaneous English authoring is retired. Current setting changes must follow the Seoul-only world and removal of the wuxia system, without rewriting sealed historical records or claiming that the editorial migration is complete. Use a dedicated branch and PR; only the owner merges `main`. Source approval, publication admission, generation and operational deployment are distinct gates.

## Testing rules

The former `test:*` npm scripts/workflows were removed by owner decision (2026-10-26); retained InkOS adapter tests are separate, not proof of publication. Do not add new test scripts. Use PostgreSQL generation/publication checks described in [README.md](README.md); `cast:verify` and `lore-json-validate.mjs` inspect explicitly supplied external SQLite migration inputs, not current production PG heads. Keep one-off verification out of the committed tree. Normal generation needs separate public/private PostgreSQL connections and the configured external inputs. Do not bypass missing secrets or provenance checks. Deployment caller and HTTP observations are documented in [deploy/README.md](deploy/README.md).

Retained adapter regression files are not self-contained in a default checkout: their fixture/schema reader opens the removed, hardcoded `data/canonical/wiki-cast.sqlite` through `authoring-schema-documents.mjs`. That reader does not honor `WIKI_DOCUMENT_DB`, so supplying an external path alone cannot fix these regressions. They currently fail on this deleted-path dependency and require a separately scoped code migration before they can run without restoring the obsolete database. Do not restore it, bypass the tests, infer a PG runtime fallback, or claim these database-open failures validate current production behavior. InkOS CLI/pin smoke coverage is distinct from adapter/database regression coverage.

## Historical person sheets

Normal `npm run generate` and `npm run build` read PostgreSQL typed preservation-sheet tables and verify stored revision, provenance, record and numeric seals. They do not load `vendor/issued-history/` files as runtime authoring inputs. That directory retains immutable historical ledger/citation bytes, not an alternative current canon. Other external generation inputs still require the configured parent checkout or `SEOUL_KENSHI_ROOT` where applicable.

The archived revisions are `ce173686bcba220cd2a7dedfb5c78b941bf3c151` and `5f34d92d54ca56b1f6c8f117cc6cbe8eda0067e4`; preservation metadata and seals are managed in the database, not a `scripts/issued-preservation-baseline.json` file. `WIKI_DOCUMENT_DB=/absolute/external/diagnostic.sqlite node scripts/import-issued-history.mjs` is an explicit, approval-scoped maintenance import from Git objects using external diagnostic metadata. It verifies payload hashes before overwriting archived inputs. It is not a normal build, a production migration, or a rebaseline command. Do not edit the sealed corpus or historical affiliation/numeric bytes to match current heads.

Current person details are regenerated from PostgreSQL typed records whose logical namespaces are described under `lore/`; those logical `.json` paths are not authoring files to restore. Current public person details do not expose historical `personSheet` or `gurps` fields. Stored historical records and numbers remain immutable, nonoperative evidence, not current affiliation or a new opposed-d10/ability/skill assignment. Preservation checks and public current-profile validation are separate contracts.

`node scripts/check-preserved-generation.mjs` is a retained, state-changing integration helper: it clears the sheet-specific override variables, runs the standard build and a second generation, and compares person-detail hashes. It still asserts a fixed historical count of 1,022 files; that is not a newly measured current person denominator or a reliable general PG-authority check. It requires normal public/private PG and other generation inputs and changes generated output. Do not run it as a read-only documentation check or use its count as current canon; review its assumptions against the exact source revision before an authorized preservation rehearsal.
