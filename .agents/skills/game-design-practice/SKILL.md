# 게임 설계·시나리오 작업 지침

소유자가 준 "기획팀 4역할 운영 매뉴얼"(2026-11-13)을 참고 자료로 삼아, 그대로 옮기지 않고 다시 정리한 지침이다. 소유자 지시(원문): "참고 만 해야지 그대로 운영 지침을 가져 가면 안되고 이것을 기반으로 우리가 알고 있는 더 나은 방식들 omo 나 claude에서 뉴트럴하게 쓸수 있게 정리 해야해", "모든 설정을 다 그대로 쓰면 안됩니다. 내가 넣은 프롬프트는 지엽적 최적화가 있기 때문에 취사 선택하여 써야 합니다." 무엇을 남기고 뺐는지는 10절에 있다.

## 0. 이 지침을 쓰는 법

- **관점(lens)으로 일한다. 역할극을 하지 않는다.** 아래 일곱 관점은 산출물과 합격 기준의 묶음이다. 한 에이전트가 차례로 맡아도 되고, 서브에이전트를 띄울 수 있는 환경이면 관점마다 나눠 맡겨도 된다. 어느 쪽이든 산출물과 합격 기준은 같다.
- **호출:** 사용자가 관점 이름(컨셉, 시스템, 서사, 밸런스, 레벨·콘텐츠, UI, 아트)을 부르면 그 관점의 산출물로 답한다. "기획해 줘"처럼 관점 없이 부르면 1절의 흐름을 따른다.
- **도구 중립:** 특정 하네스의 도구 이름, 특정 웹 서비스 조작, 특정 모델을 전제하지 않는다. 이미지 생성, 검색, 서브에이전트처럼 환경마다 다른 능력은 "그 환경에서 허용된 경로"로 쓴다. 프로젝트가 정한 경로(예: 저장소 지침이 지정한 이미지 생성 경로)가 있으면 그것을 따른다.
- **원리와 휴리스틱을 구분한다.** 이 지침의 원리(근접성, 피츠, 힉, MDA 등)는 어디서나 쓴다. 숫자가 붙은 규칙(선택지 개수, 시간, 배수, 크기)은 "기본 휴리스틱"이다. 프로젝트가 근거(플레이테스트, 시뮬레이션, 장르 관례)를 들면 바꿀 수 있고, 바꿀 때는 근거를 적는다. 휴리스틱에는 [휴리스틱] 표시를 붙였다.
- **프로젝트 프로필이 우선한다.** 플랫폼, 입력 장치, 사업 모델, 톤, 저작권 표기, 정본 문서는 프로젝트마다 다르다. 9절의 프로필을 먼저 채우거나 읽고, 이 지침의 조건부 규칙은 그 프로필에 맞는 것만 적용한다.

## 1. 흐름 (순서가 아니라 의존 관계)

```
컨셉(필러) ─▶ 시스템 ─▶ 밸런스 ─▶ 레벨·콘텐츠
     │          │  ▲        │            │
     │          ▼  │        ▼            ▼
     └──────▶ 서사 ─┘     UI ⇄ 아트 ─▶ 검증(플레이테스트·시뮬레이션) ─▶ 교차 검토 ─▶ 반영
```

- 컨셉의 필러가 모든 판단의 기준이다. 필러 없이 다른 관점을 시작하지 않는다.
- 시스템과 서사는 함께 돈다. 서사가 보상 구조와 어긋나면(루도내러티브 불일치) 시스템 쪽 수정까지 같이 낸다.
- 밸런스 수치는 시스템 명세가 정한 변수에만 붙는다. 명세에 없는 변수를 밸런스가 새로 만들지 않는다.
- UI와 아트는 한 쌍이다. 공동 토큰 한 벌을 쓴다(6절).
- 검증은 마지막 한 번이 아니다. 각 관점의 산출물마다 그 관점의 합격 기준으로 먼저 검증하고, 끝에 교차 검토(8절)를 한다.

## 2. 관점별 산출물과 합격 기준

### 2.1 컨셉 — "왜 이 게임인가"

- 하이컨셉 한 줄("플레이어는 ~가 된다", "X 같은데 Y가 다르다"), 코어 판타지(플레이어가 느낄 단 하나의 감정), 디자인 필러 3~4개, "이 게임이 아닌 것" 목록(분쟁 판정 기준).
- MDA 목표 미학을 먼저 고른다(감각, 판타지, 서사, 도전, 동료애, 발견, 표현, 소일 가운데 주 1~2개). 카이와 놀이 유형(4절) 주 1개 + 보조 1개, 파이디아↔루두스 위치.
- 타깃 유저, 플랫폼·입력 장치, 세션 길이, 레퍼런스 2~3개와 각각과의 차이, USP, 사업 모델(프로필에 따름), 톤앤매너(아트·사운드 무드).
- 산출물: 1쪽 컨셉 문서.
- 합격 기준: 30초 안에 설명된다. 대표 화면 한 장으로 장르와 재미가 보인다. 필러끼리 모순이 없다. "아닌 것" 목록이 실제로 무언가를 배제한다.

### 2.2 시스템 — "어떻게 노는가"

- 루프 셋: 코어(초~분), 메타(턴·세션·일), 장기 목표. 각 루프가 한 번 돌 때 무엇을 얻는지.
- 시스템마다 입력 → 판정 → 결과, 상태 전이, 예외, 실패 조건. 데이터 테이블 스키마(키, 타입, 범위, 단위, 출처 문서).
- 콘텐츠 구조: 모드, 해금 순서, 첫 경험(FTUE) 흐름. 화면 목록과 전환도(UI 관점에 넘김).
- 전략 게임 점검(조건부, 프로필이 전략·시뮬레이션일 때): 결정마다 "의미 있는 선택"인가(대안이 각각 다른 상황에서 최선인가), 선두 독주(양의 피드백)와 따라잡기 장치, 정보 공개 범위(안개, 숨긴 값), AI가 읽히는가(플레이어가 상대의 의도를 추론할 수 있는가), 턴 하나에 드는 결정 수.
- 사업 모델 노출 지점은 프로필에 과금이 있을 때만 적는다. 리텐션과 공정성을 해치는 위치는 쓰지 않는다.
- 산출물: 시스템 명세, 흐름도, 데이터 테이블 정의.
- 합격 기준: 프로그래머가 질문 없이 만들 수 있다. 엣지케이스가 적혀 있다. 지배 전략 후보를 스스로 찾아 적었다. 첫 몇 분 안에 핵심 재미가 한 번 돈다.

### 2.3 서사 — "왜 계속 하고 싶은가"

- 세계관 바이블(규칙, 역사, 세력), 캐릭터 시트(욕망, 결핍, 말투, 다른 인물과의 관계), 메인 플롯 구조, 챕터별 감정 곡선을 난이도·보상 곡선과 맞춘 표.
- 분량 통제: 좁은 분기와 병목(branch and bottleneck). 시스템이 사건을 만들어 내는 게임(전략·시뮬레이션)은 스토리렛 또는 질 기반 서사(조건을 가진 짧은 이야기 조각을 인물·세계 상태로 고르는 방식)를 쓴다.
- 서사 건축(Jenkins): 환기·수행·내장·창발 네 방식. 환경이 "무엇이 일어났나"를, 대사가 "왜 일어났나"를 맡는다. 핵심 정보는 세 곳 이상에 겹쳐 둔다.
- 텍스트 전부가 서사의 일이다: UI 문구, 튜토리얼, 아이템·유닛 설명.
- 금지: 루도내러티브 불일치, 설명 덤프, 의미 없는 선택지, 대사만으로 구분되지 않는 인물. 다른 작품·실제 역사의 비유를 세계 안 문장에 그대로 옮기는 것(비유는 구조 설명일 뿐이다).
- 산출물: 세계관 문서, 캐릭터 시트, 스크립트(Ink·Yarn처럼 분기와 조건을 담을 수 있는 형식 권장).
- 합격 기준: 이름을 가려도 말투로 누군지 안다. 모든 선택지가 서로 다른 의도를 가진다. 클라이맥스가 난이도·보상 피크와 같은 자리에 있다.

### 2.4 밸런스 — "얼마나, 언제"

- 모든 수치는 공식과 근거를 단다. 근거 없는 수치는 "잠정"으로 표시하고 목록에 올린다.
- 전투: DPS, 유효 체력(EHP), TTK = 적 EHP ÷ 아군 DPS, 스펙 브레이크포인트. 부대 전투(조건부)는 란체스터 법칙(선형·제곱)으로 병력 수와 질의 교환 비율을 시뮬레이션한다. 상성은 비순환(가위바위보형) 행렬로 적고, 열마다 합이 한쪽으로 쏠리지 않는지 본다.
- 성장: 곡선 꼴(선형·지수·로그)과 고른 이유, 파워 커브.
- 경제: 자원마다 수도꼭지(faucet)와 배수구(sink) 표, 턴·일당 순증가, 인플레이션 감시. 흐름을 그림(Machinations식 노드·흐름도)으로 남긴다. 수도꼭지와 배수구의 시기 배분은 필러가 정한다. 풍족감이 목표면 초반 수도꼭지 우위가 흔한 선택이고, 결핍이 주제면 처음부터 "모자람이 결정을 만든다"를 수치로 증명한다. 어느 쪽이든 그 선택의 근거를 적는다.
- 난이도 곡선: 단계별 TTK·클리어율 또는 턴별 위협 지표. 급등 구간(기본 휴리스틱: 전 단계의 1.5배 이상 [휴리스틱]) 앞에는 쉬는 구간을 둔다.
- 운(조건부): 기대값, 천장, 확률 공개. 과금 확률은 법적 공개 의무를 따른다.
- 산출물: 공식이 들어간 밸런스 시트, 재실행 가능한 시뮬레이션 스크립트(시드 고정), 튜닝 기록.
- 합격 기준: 지배 전략이 시뮬레이션에서 나오지 않는다. 막히는 벽의 위치와 이유가 적혀 있다. 1시간·1세션·1주(또는 캠페인 전체) 예상 진행이 있다.

### 2.5 레벨·콘텐츠 — "어떤 순서로, 어떤 판을"

- 학습 4단계: 소개(안전하게 하나만) → 연습 → 응용(다른 요소와 조합) → 시험.
- 한 판 = 한 아이디어. 판마다 "이 판의 핵심 질문" 한 줄.
- 페이싱: 긴장↔이완, 새 요소가 나오는 판은 다른 난이도 요소를 낮춘다.
- 동선·시선: 유도선(연속성), 전경-배경, 조명·색으로 말 없이 가르친다. 화면 배치는 입력 장치를 따른다(9절 프로필: 터치면 엄지 영역, 마우스면 시선 흐름과 커서 이동 거리).
- 레벨 표: id, 핵심 질문, 새 요소, 변수값, 예상 시간·클리어율, 서사 비트.
- 절차 생성: 시드 고정, 풀 수 있음 검증, 난이도 지표 자동 측정.
- 산출물: 레벨 표, 긴장 곡선, 화이트박스 또는 종이 프로토타입, 플레이테스트 기록.
- 합격 기준: 처음 보는 사람이 글 없이 이해한다. 막힘의 원인이 실력인지 정보 부족인지 구분된다. 같은 판이 반복처럼 느껴지지 않는다.

### 2.6 UI — "어떻게 쓰이는가"

- 와이어프레임(프로필의 화면 비율과 입력 장치 기준), 화면 목록과 전환도, 정보 위계(무엇을 3초 안에 읽어야 하나).
- 디자인 토큰: 색(HEX와 용도), 타이포 스케일, 간격 그리드, 모서리, 그림자, 모션 시간·이징. 프로젝트에 토큰 원천이 있으면 그것만 쓰고, 없는 값은 "토큰 추가 요청" 표로 제안한다.
- 컴포넌트와 상태: 버튼(주·보조·고스트 × 기본·호버/눌림·비활성·초점), 시트, 토스트, 진행바, 카드.
- 접근성: 대비 4.5:1 이상(큰 글자 3:1), 색만으로 정보를 전하지 않는다, 최소 글자 크기, 모션 줄이기, 키 다시 지정, 자막과 글자 크기 조절. 게임 접근성 지침(Game Accessibility Guidelines, Xbox Accessibility Guidelines)을 점검표로 쓴다.
- 모션: 피드백은 짧게, 보상 연출은 그보다 길게, 실패는 짧고 부드럽게. 기본값 피드백 100~300ms, 보상 1~1.5초 [휴리스틱]. 모션 줄이기 설정을 존중한다.
- 산출물: 와이어프레임, 토큰 표, 컴포넌트 상태표, 아트 요청서, 구현 코드(레이아웃·텍스트·상태 로직).

### 2.7 아트 — "어떻게 보이는가"

- 아트 바이블 1장: 톤, 색 체계와 바탕색(HEX, UI 토큰과 같은 값), 선 굵기, 명암 방식, 금지 요소.
- 에셋 명세: 파일명 규칙, 용도, 표시 크기와 내보내기 크기, 투명 배경 여부, 상태 변형.
- 생성 규칙(어떤 생성 경로든 같다): 요청 하나에 에셋 하나(또는 같은 스타일 시트 한 장). 매 요청 첫머리에 스타일 고정 블록. 비율·시점·투명 배경·여백·"글자와 워터마크 없음"을 적는다. 기준작 한 장을 승인한 뒤 같은 스타일로 이어 간다. 색은 HEX로 지정하고 생성 뒤 팔레트로 보정한다. 모든 결과에 출처 기록(모델·요청·시드 또는 요청 id·해시·날짜·점검한 규칙)을 남긴다.
- 검수: 실제 표시 크기 가운데 가장 작은 크기에서 실루엣이 읽힌다(아이콘이면 흔히 32px [휴리스틱]). 같은 기능 = 같은 색·모양. 가장자리 잔여 배경이 없다. 실존 게임·브랜드 스타일 모사, 작가명 지정, 저작권 의심 요소, 검수 없는 반영을 금한다.
- 연동: 트리밍 → 배율별 리사이즈 → 압축 포맷 변환 → 게임의 에셋 교체 지점에 연결.

### 2.8 UI ↔ 아트 협업

- UI가 아트에 넘기는 요청서: 에셋마다 파일명, 놓일 화면과 영역, 표시 크기, 내보내기 크기, 배경, 상태 변형, 위에 얹힐 UI의 안전 영역.
- 아트가 먼저 기준작 한 장을 내고, UI가 실제 화면에 얹어 가독성·대비·크기를 본다.
- 공동 토큰 한 벌. 한쪽이 바꾸면 양쪽 문서를 같은 변경에서 고친다.
- 경계: 아트 = 그림(오브젝트, 배경, 일러스트, 아이콘 원화). UI = 레이아웃, 텍스트, 버튼, 상태, 애니메이션. 그림 안에 글자를 넣지 않는다(번역·수정 대비).
- UI는 아트가 오기 전에 자리 표시(벡터·점선)로 먼저 구현하고, 파일명만 맞으면 교체되게 한다.

## 3. 지각·인지 원칙 (모든 관점이 적용하고, 어디에 썼는지 적는다)

| 원칙 | 핵심 | 대표 적용 |
|---|---|---|
| 근접성 | 가까우면 한 묶음 | 관련 정보·버튼은 묶고 위험 동작은 떼어 놓기. 같은 등급 수치는 한 표에 |
| 유사성 | 같은 색·모양 = 같은 기능 | 세력·병종·상태 색 체계 |
| 연속성 | 시선·동선 유도선 | 레벨 동선, 화면 읽는 순서 |
| 폐쇄성 | 빈칸을 스스로 채움 | 도감·세트 빈칸, 다 말하지 않는 서사 |
| 전경-배경 | 상호작용 대상은 배경과 대비 | 클릭할 것과 장식의 구분 |
| 대칭성 | 대칭은 안정·공정, 비대칭은 긴장 | 대칭 시작 조건, 비대칭은 상성 근거로 상쇄 |
| 공동운명 | 함께 움직이면 한 무리 | 부대·적 무리 표현 |
| 친숙성 | 익숙한 꼴이 먼저 읽힘 | 장르 문법을 빌리고 한 가지만 비튼다 |

원칙끼리 충돌하면(가까운데 색이 달라 묶음이 헷갈림 등) 교차 검토에서 반드시 지적한다.

- **자이가르닉:** 끝내지 못한 일이 더 오래 기억된다. 세션을 끝낼 때 "하던 일"이 보이게 하고, 이어하기를 첫 화면에서 가장 찾기 쉬운 자리에 둔다. 동시에 열린 미완은 적게 유지한다(기본 3~5개 [휴리스틱]; 전략 게임은 진행 중인 일이 본래 많으므로 "지금 볼 것" 목록으로 묶어 같은 효과를 낸다). 미완은 기대여야 하고 불안이면 안 된다(끝없는 미완, FOMO, 다크패턴 금지).
- **피츠:** T = a + b·log₂(D/W + 1). 자주 쓰는 조작은 크고 가깝게, 위험한 확정은 작고 멀게. 화면 가장자리는 "무한 크기"다. 입력 장치에 맞춘다(터치 최소 44pt/48dp, 마우스는 이동 거리와 단축키, 패드는 초점 이동 횟수).
- **힉:** T = b·log₂(n + 1). 선택지 수는 결정 시간을 늘린다. 실시간 판단이 필요한 화면은 주요 선택을 적게(기본 3~5개 [휴리스틱]), 나머지는 단계적 공개로 둔다. 추천·기본값을 표시한다. 실시간 조작 중 선택은 적게, 턴·정비 화면은 많아도 된다. "깊이는 많게, 동시 노출은 적게"를 필러로 둘 수 있다.
- 의도적 역이용(시간 압박 속 다수 선택, 실수 유도 퍼즐)은 근거를 적을 때만 허용한다.

## 4. 놀이 분류 (카이와, 『놀이와 인간』, 1958)

| 유형 | 핵심 재미 | 설계 장치 |
|---|---|---|
| 아곤(경쟁) | 실력으로 이김, 공정한 조건 | 공정한 시작, 실력이 드러나는 판정, 기록·리플레이 |
| 알레아(운) | 결과를 운에 맡기는 기대 | 기대 연출, 운이 실력을 완전히 덮지 않게, 확률 공개 |
| 미미크리(역할) | 다른 존재가 되어 봄 | 정체성 표현, 선택이 반영되는 세계 |
| 일링크스(현기증) | 감각·속도·몰입 | 타격감, 카메라, 속도감(멀미·피로 한도) |

- 축: 파이디아(자유·즉흥) ↔ 루두스(규칙·목표·숙련).
- 밸런스는 실력 대 운의 기여 비율(%)을 적는다.
- 타락 형태를 경계한다: 승부 집착, 도박 중독(확률 공개·과금 상한), 정체성 혼동, 중독.

## 5. 동기·몰입 이론 (원전 요약)

- **MDA** (Hunicke·LeBlanc·Zubek 2004): 목표 미학 → 다이내믹 → 메커닉 순으로 역산한다. 플레이어는 반대 방향으로 경험한다. 양의 피드백(선두 독주)을 점검한다.
- **GameFlow** (Sweetser·Wyeth 2005): 집중, 도전, 실력, 통제, 목표, 피드백, 몰입, 사회의 8요소를 출시 전에 1~5점으로 자가 평가한다. 도전이 가장 무겁고, 페이싱은 플레이테스트로 검증한다.
- **서사 건축** (Jenkins 2004): 설계자는 이야기꾼이 아니라 서사 건축가다(2.3절).
- **SDT** (Ryan·Rigby·Przybylski 2006): 끌림 = 자율성·유능감·관계성. 유능감이 가장 강하고, 조작은 입장료일 뿐이다. 보상은 정보로 주고 통제로 주지 않는다.
- **DDA / Hamlet** (Hunicke·Chapman 2004): 연속 실패(flailing)를 감지하면 꼭 필요한 만큼, 티 나지 않게, 미리 보정하고, 개입은 점점 줄인다. 아곤이 주 유형인 게임이나 공정성이 필러인 게임에서는 보정을 끄거나 플레이어에게 알린다.

(소유자 매뉴얼의 논문 목록은 DDA 항목에서 끊겨 있었고 참조된 `PAPERS.md`는 찾지 못했다. 위 다섯 항목은 각 원전을 기준으로 적었다. 목록이 더 있으면 같은 꼴로 덧붙인다.)

## 6. 근거와 승인 (이 지침이 매뉴얼에 보태는 운영 규칙)

- 사실·수치·외부 게임 규칙은 출처와 신뢰 등급(직접 확인, 데이터 확인, 문서·추론, 미확정)을 단다.
- 지어낸 이름·수치·설정은 "잠정"으로 표시하고 한 원장에 모은다. 소유자가 답하기 전에는 승인된 것으로 쓰지 않는다.
- 소유자가 든 다른 작품·역사의 비유는 구조 설명이다. 세계 안의 낱말로 옮기고 비유 낱말은 결정 기록에만 남긴다.
- 실존 브랜드·다른 게임의 고유 명칭은 쓰지 않는다. 수치는 공개된 게임 값을 참고할 수 있지만 출처를 단다.
- 검증은 실제로 실행한 범위만 주장한다(시뮬레이션 실행, 화면을 실제로 보고 읽음, 빌드 통과). 통과시키려고 기대값이나 입력을 바꾸지 않는다.

## 7. 플레이테스트와 검증

- 종이·화이트박스 단계에서 생각 말하기(think-aloud) 테스트, 고칠 수 있는 문제는 바로 고치고 다음 참가자로 넘어가는 반복 방식(RITE).
- 지표: 단계별 클리어율·시간, 이탈 지점, 선택 분포(지배 전략 징후), 경제 순증가.
- 시뮬레이션은 시드를 고정하고 다시 돌릴 수 있게 둔다.
- 사람 플레이테스트를 할 수 없는 환경에서는 그 사실을 적고, 시뮬레이션과 규칙 대조, 화면 읽기 검증으로 대신한 범위를 밝힌다.

## 8. 교차 검토 점검표 (끝에 모두가 한 번에)

- 놀이 유형: 주·보조 유형과 파이디아↔루두스 위치가 컨셉·시스템·수치에 같게 반영됐나.
- 피츠: 자주 쓰는 조작은 크고 가까운가, 위험 확정은 멀고 작은가, 입력 장치 최소 크기를 지켰나.
- 힉: 화면 종류(실시간·턴·정비)에 맞게 동시 노출 선택지를 줄였나, 기본값·추천이 있나, 휴리스틱에서 벗어난 곳은 근거를 적었나.
- 자이가르닉: 끌 때 "하던 일"이 남는가, 그것이 불안이 아닌 기대인가.
- 게슈탈트: 첫 화면 3초 안에 묶음과 우선순위가 읽히나, 적용 위치를 적었나.
- 필러: 모든 시스템·이야기·수치가 필러를 지지하나.
- 서사 × 밸런스: 클라이맥스 = 난이도 피크 = 보상 피크.
- 시스템 × 밸런스: 코어 루프 한 번이 보상으로 체감되는 시간.
- 서사 × 시스템: 튜토리얼과 UI 문구가 세계의 톤을 지키나.
- 근거: 모든 수치에 공식·출처가 있나, 잠정 항목이 원장에 있나.
- 접근성: 대비, 색 외 단서, 글자 크기, 모션 줄이기, 키 다시 지정.
