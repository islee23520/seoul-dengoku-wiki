## Local checks

Use npm install --ignore-scripts in this package, then install runtime dependencies in the canonical source packages (npm install --prefix ../avatar-gen/portrait/generator --ignore-scripts --package-lock=false and npm install --prefix ../tools/people-cli --ignore-scripts --package-lock=false). The server directly imports canonical pure TypeScript APIs, not the historical generator CLI. npm run typecheck, npm run lint, npm run build, and bun test verify the backend. npm start starts the Node bundle. Bun install currently misresolves the generator's nested file dependency; npm resolves the local links correctly.

### Private native worker packaging

The build validates `native-moss/manifest.json` and copies only its finite
hash/size-checked regular source files plus that manifest to
`dist/private/native-moss/`. It adds those paths to private release artifacts
and TAR/ZIP, never `publicFiles`. Unlisted tests, cache, credentials, model
weights and `.omo` files are not copied. Runtime dependencies remain installed
on the fixed host; packaging does not install Python/Bun/Zod/model assets.
Manifest drift fails `NATIVE_PACKAGE_FILE_DRIFT` rather than repinning a source.

`PORTAL_BUILD_OUTPUT` selects a local build directory, and
`PORTAL_BUILD_NATIVE_SOURCE` selects an explicitly prepared manifest-bearing
local source snapshot for packaging tests. Neither is a browser/server runtime
input. A passing temporary candidate build does not qualify the production
worker or approve its pins.

`native-moss-package.ts` exports `nativeMossPrivatePath` and
`nativeMossPackageRoot(moduleURL)` for provider integration: source TS resolves
`../native-moss/`; a built `.mjs` resolves `./private/native-moss/` beside the
server bundle. Current provider lookup still uses its old source-relative path;
the provider owner must adopt the resolver before packaged native dispatch.
The server's fixed authenticated release-download artifact schema also needs
its separately owned integration update for the additional private payloads.
Direct public/static native-file URLs remain unavailable.

## Configuration

The default is a service on each user's own computer at http://127.0.0.1:18765/tools/. No GitHub account, OAuth app, central deployment or shared provider credentials are required. `PORTAL_MODE=local` is explicit local mode; a configured `PORTAL_PUBLIC_URL` without a mode retains historical hosted compatibility. Local mode binds 127.0.0.1 unless private-network access is explicitly enabled below. It rejects any other Host, any nonmatching Origin and cross-site browser requests. The default private storage is the native user's home directory under `.seoul-dengoku-tools/portal`; `PORTAL_STORAGE_PATH` overrides it.

GET /tools/api/auth/session bootstraps the local numeric owner 1 with a boot-bound signed HttpOnly SameSite=Strict cookie and returns `{authenticated:true,user:{id:"1",login:"local"},csrfToken,mode:"local"}`. All mutations require the exact local Origin and X-CSRF-Token. Restart invalidates every old session and memory connection. Logout revokes both; another session GET can bootstrap immediately without OAuth or restart.

In local mode POST /tools/api/connections strictly accepts `{baseUrl,apiKey}`. Both are explicit user input; the key must be nonempty. Only loopback HTTP or explicitly selected HTTPS API base URLs are accepted, with no embedded credentials, query or fragment and no redirect following. `/images/edits` is appended to the base URL. Connecting makes zero provider requests. The URL/key stay only in server memory and are cleared on revocation; ambient OpenAI/CLI-proxy tokens never supply dispatch authority. Responses, logs and stored artifacts never contain the key. GET connections returns `{mode:"local",endpoints:[],connection}`; the credential-free snapshot identifies `openai-compatible-http.v1`, not MCP.

Local dispatch reuses canonical sendPortraitRequest and projection binding through a private per-job authenticated loopback relay. The relay forwards the exact canonical multipart bytes to the chosen provider and bounds request capture to 16 MiB and response capture to 12 MiB, with no retry. `provider-request.bin`/`provider-response.bin` retain exact body bytes with separate credential-free transport metadata; canonical request, receipt, PNG and strict portal receipt remain private. Incomplete or uncertain dispatched results are UNKNOWN. The existing strict single-job, batch, evaluation and replay contracts remain in force.

## Opt-in LAN mDNS or Tailscale IP serving

`PORTAL_NETWORK_ACCESS=true` permits `PORTAL_HOST` to select exactly one IPv4 address assigned to a noninternal interface on this machine. Only RFC1918 LAN addresses (10/8, 172.16/12, 192.168/16) or the Tailscale address range 100.64/10 are accepted. Interface membership is checked while loading configuration and immediately before listening. `0.0.0.0`, public IPs, unowned IPs and IPv6 are rejected. The 100.64/10 check proves local address ownership, not that Tailscale is installed or a remote peer is authorized; the operator must select the actual Tailscale IP and configure tailnet access controls. The service neither enables Tailscale nor changes existing Serve, MagicDNS, proxy or firewall configuration.

For LAN discovery on macOS, choose the actual LAN interface IP and a unique lowercase single-label `.local` hostname:

```bash
PORTAL_MODE=local PORTAL_NETWORK_ACCESS=true PORTAL_HOST=192.168.0.218 \
  PORTAL_LOCAL_HOSTNAME=dengoku-tools.local PORTAL_MDNS=true \
  node dist/server.mjs
```

Replace the example IP with your machine's own address. Open `http://dengoku-tools.local:18765/tools/` from a client on that same multicast LAN, or use `http://192.168.0.218:18765/tools/`. `PORTAL_MDNS=true` invokes native `/usr/bin/dns-sd -i <selected interface> -P` to register `_http._tcp.local`, TXT `path=/tools/`, the actual bound port, and exactly one A record mapping the configured hostname to the selected listener IP. It does not publish the machine's other LAN, tailnet or IPv6 addresses. Native address and service registration acknowledgments must both arrive before `PORTAL_READY`; registration failure closes the listener. Shutdown terminates the registration process and withdraws its records. A conflicting hostname fails explicitly. Native service-name auto-renaming is rejected rather than silently changing the contract. No Bonjour npm dependency is used because its standard publisher enumerates every host interface.

mDNS advertising currently requires macOS and its native DNS-SD executable; opting into it on another platform fails with `MDNS_PLATFORM_UNSUPPORTED`. Private-IP serving itself uses Node network interfaces and is not macOS-specific. The native platform limit is explicit, not a claim of portable Bonjour installation. A manually provisioned `.local` name can be accepted with `PORTAL_LOCAL_HOSTNAME` while `PORTAL_MDNS=false`, but that setting alone creates no DNS records.

mDNS `.local` discovery uses LAN multicast and does not cross Tailscale. Do not advertise a LAN hostname for a listener bound exclusively to a tailnet IP: that configuration is rejected with `INVALID_MDNS_CONFIG`. Select tailnet IP mode separately:

```bash
PORTAL_MODE=local PORTAL_NETWORK_ACCESS=true PORTAL_HOST=100.71.30.111 \
  PORTAL_MDNS=false node dist/server.mjs
```

Replace the example with this machine's `tailscale ip -4`, then open `http://100.71.30.111:18765/tools/` from an allowed tailnet peer. One process selects one listener address; these examples are alternative modes, not simultaneous LAN and tailnet listeners. A `.local` alias accepted in tailnet mode still needs separately provisioned resolution and is not advertised by this service. LAN-only and tailnet-only modes do not imply that the other network can reach the bound address.

All admitted clients use the one machine-owner workspace (numeric owner 1), not independent tenants. Any client that can reach the selected address may bootstrap that owner through GET `/tools/api/auth/session`; enable access only for clients trusted to read and act on that workspace. There is no per-client credential isolation claim: sessions retain their own boot-bound memory connections and keys, while stored jobs, batches and evaluations belong to the shared owner. Transport is direct HTTP; the service does not add TLS. With network access disabled, even a remote client spoofing a loopback Host cannot bootstrap a session.

The accepted HTTP Host is exactly `<selected IP>:<actual port>` or `<configured .local hostname>:<actual port>`. Origin must equal `http://` plus that request's accepted Host, not another accepted alias, and every mutation still needs its session's CSRF token. Arbitrary Host, wrong ports, cross-site requests and mismatched Origin fail before provider or OAuth calls. Forwarded headers grant no authority. Restart and logout preserve the existing session invalidation and memory-key clearing rules.

To inspect the actual native records without claiming cross-tailnet discovery:

```bash
dns-sd -i en0 -B _http._tcp local
dns-sd -i en0 -L dengoku-tools _http._tcp local
dns-sd -i en0 -G v4 dengoku-tools.local
```

Use the selected LAN interface in place of `en0`. Each command remains open for event-driven results; stop it with Ctrl-C. `PORTAL_PORT=0` is useful for isolated QA: `PORTAL_READY` reports the actual port, which must also appear in the discovered SRV record and client URL. Real LAN discovery and remote tailnet reachability require native/client verification; fixture tests prove the registration arguments, readiness, failure cleanup and HTTP security contract, not remote DNS resolution.

## Single-owner personal HTTPS deployment

`PORTAL_MODE=personal` explicitly selects the private HTTPS portal. Local/LAN/mDNS/Tailscale defaults and historical hosted MCP behavior are unchanged. Personal mode requires `PORTAL_PUBLIC_URL` to be the exact canonical HTTPS URL ending in the configured base path, for example `https://sss.linalab.io/tools`. The fixed origin is used for request Host and browser Origin checks; forwarded host/protocol headers grant no authority.

Set `PORTAL_OWNER_EMAIL` to the exact single owner email, `PORTAL_ACCESS_ISSUER` to the canonical team URL (`https://linalab.cloudflareaccess.com`), and `PORTAL_ACCESS_AUDIENCE` to the 64-character AUD of the dedicated owner-only Access application. Do not substitute an existing contributors application's audience. `PORTAL_SESSION_SECRET` must contain at least 32 characters. `PORTAL_STORAGE_PATH` must be absolute (the private Docker workspace uses `/private`); `PORTAL_TEMPLATE_MANIFEST` and `PORTAL_TEMPLATE_PINS` are required readiness inputs. Existing original database and template mounts must remain private.

Every request, including redirects, static assets, status and unknown routes, independently requires the `Cf-Access-Jwt-Assertion` header. The backend verifies RS256 with the issuer's official `/cdn-cgi/access/certs` JWKS, matches `iss`, `aud` and the exact signed owner email, rejects expired tokens and future `nbf`, and never trusts `Cf-Access-Authenticated-User-Email`. JWKS retrieval has a 5-second timeout, no redirects/retries, a 64 KiB body bound and at most 32 RSA keys. Valid keys are cached for at most 5 minutes (bounded by upstream max-age); an unknown signing key can refresh after 30 seconds. Fetch/parse/key failures fail closed rather than accepting stale keys.

Only a verified Access request to GET `/tools/api/auth/session` bootstraps numeric owner `1` with login equal to the configured owner email. Its boot-bound portal cookie is Secure, HttpOnly and SameSite=Strict. Possessing that cookie never bypasses Access verification on a later request. Personal login/callback routes do not invoke GitHub. Mutations require the exact public HTTPS Origin and session CSRF token. Logout revokes the portal session and its in-memory provider connection; it does not log the browser out of Cloudflare Access. A new session GET requires a fresh valid Access assertion.

Personal mode optionally accepts the explicit pair `PORTAL_PERSONAL_PROVIDER_URL` and `PORTAL_PERSONAL_PROVIDER_KEY` in private server configuration. Both must be supplied together and pass the same `{baseUrl,apiKey}` validation as local connections; invalid or partial configuration fails with `INVALID_PERSONAL_PROVIDER_CONFIG`. These settings are loaded only in personal mode. Ambient OpenAI/CLIProxy variables never provide fallback credentials.

With this pair configured, a verified owner session automatically receives its own READY OpenAI-compatible connection when GET `/tools/api/auth/session` or GET `/tools/api/connections` first accesses that session. Session JSON returns only the boolean `serverProviderConfigured`; the UI hides credential entry and explains the server-owned provider. Independent owner sessions may each bind this configured provider, but every connection read and outbound request still requires its exact signed session. Logout revokes only that session's connection. Explicit disconnect leaves a REVOKED tombstone: refresh does not reconnect it, and a new authenticated session gets its own connection. POST connections cannot replace the configured provider. Configuration and automatic connection make no provider calls.

Without this pair, personal mode retains explicit per-session `{baseUrl,apiKey}` entry through the protected UI and the existing single-owner connection reservation. GET connections returns `{mode:"personal",endpoints:[],connection}` in either case. Provider keys are never returned or saved in artifacts; configured credentials remain in private server configuration and memory, while revocation clears each session's dispatch authority. Hosted mode retains its reviewed MCP endpoints.

## ComfyUI as a second, distinct provider connection

MOSS-Image SFT with the verified style LoRA (`moss-image-sft-style-lora.v1`, endpoint `comfyui-moss-style`) is the default ComfyUI workflow. Plain `moss-image-sft-text.v1` remains available for explicit comparison. New ZImage connect or generation requests return `COMFY_WORKFLOW_RETIRED` (422). Stored ZImage jobs retain their original labels, images, evidence verification and review/evaluation support; no job artifacts are removed.

The style workflow inserts one `LoraLoaderModelOnly` at node 10, strength 1, with trigger `seoul dengoku portrait style` in the deterministic prompt. Before readiness and each submission the Windows portal streams SHA-256 over the actual installed diffusion, encoder, VAE and LoRA files at server-owned paths resolved from the installed Comfy metadata API. Missing or mismatched assets fail before `/prompt`. `comfy-assets.json` retains the measured proof; canonical and delivery receipts bind its SHA and the exact LoRA filename, hash, strength and trigger. Evidence verification checks the proof and exact graph. Compatibility is proven, but technique-only qualification and owner visual approval remain pending. Native output and 340x510 delivery remain opaque for RGB SaveImage output; no alpha-zero postprocess is claimed. Later derivatives can bind the job UUID, `nativeSHA`, `sourcePngSHA`, delivery `responseSHA`, receipt `transformation.canonicalReceiptSHA` and sealed result `pngSHA`/`receiptSHA` returned by `/tools/api/jobs/:id/result`.

`PORTAL_COMFYUI=true` (local or personal mode only; any other mode fails with `INVALID_COMFYUI_CONFIG`) registers the server-owned ComfyUI endpoint `comfyui-moss` with protocol `comfyui-http.v1` and the single workflow `moss-image-sft-text.v1`. The destination (`src/comfyui-provider.ts`, `COMFY_ENDPOINT`) is a reviewed constant: browsers never supply a URL, graph, model name or credential, and no API key is involved. The native Windows launcher `install/start-personal-native.mjs` only forwards allowlisted environment keys, so a deployment that wants ComfyUI must add `PORTAL_COMFYUI` to that allowlist and to the launch config `environment`; without it the flag is silently absent and the UI shows no ComfyUI option.

The connection registry keeps one live connection per transport protocol per session, so the existing OpenAI-compatible (CLIProxy) account connection and a ComfyUI connection are READY side by side. POST `/tools/api/connections` with `{provider:"comfyui",workflow:"moss-image-sft-text.v1"}` verifies readiness only (`/system_stats`, `/object_info`, required model/node availability) under the signed session and returns `{connection, readiness:{state,workflow,models}}`; it never submits a prompt, and the usual owner lease, `JOB_RUNNING` and `OWNER_DISPATCH_UNCERTAIN` gates apply. GET `/tools/api/connections` adds `comfyui:{available,workflows,connection,readiness}`; the OpenAI `connection`/`provider` fields are unchanged. DELETE `/tools/api/connections/:id`, logout and boot invalidation revoke a Comfy connection like any other; saving or deleting the OpenAI account credential revokes only OpenAI-compatible connections.

POST `/tools/api/generations` accepts `providerModel:"comfyui:moss-image-sft-text.v1"` plus an optional integer `seed` (server-random when omitted) and requires `connectionId` to be the Comfy connection; a workflow on an OpenAI connection or a GPT model on the Comfy connection fails with `CONNECTION_PROVIDER_MISMATCH`. Batches and workstations stay OpenAI-compatible. The job transports only the retained authored projection text (`projection.txt`), never the wiki PNG or template reference images, and every outbound call rechecks the live owner/session binding; revocation before submit yields `FAILED`, after submit `UNKNOWN`, and an UNKNOWN prompt is never resubmitted. The private job directory retains `comfy-request.json` (exact submitted graph), `comfy-history.json`, `comfy-response.json`, `provider-native.png` (exact 1024x1536 SaveImage bytes), `provider-source.png` (alpha-expanded RGBA), `provider-canonical.receipt.json`, `candidate.png` (340x510) and `candidate.png.receipt.json`. Result sealing and evaluations accept the ComfyUI receipt as its own contract (`provider`, `workflow`, `promptId`, `seed`, `status:"draft"`), recompute every hash and the exact server-owned graph from the retained bytes, and never read a Comfy draft as GPT evidence. The workflow is a text draft with no identity-photo fidelity or SD3.5 style qualification; results remain HOLD candidates with approval NONE.

Terminate HTTPS at the trusted Cloudflare Access reverse proxy. The origin receives private HTTP and must not be directly published: Docker may bind `PORTAL_HOST=0.0.0.0` inside the container only with explicit personal mode, while the host port is published to `127.0.0.1:18765` only. Preserve the exact public Host and Access assertion on the proxy hop. A direct anonymous HTTP request is denied by the backend even if it spoofs that Host. `cloudflared` may additionally require the application's AUD via `originRequest.access.required`, but backend verification remains mandatory. DNS, Access policy, tunnel configuration and the private provider service are operator deployment responsibilities.

## Review-first workspace

The workspace opens in Review and separates four tasks: Review, Single production, Batch composition and Execution status. The result strip contains results known in this session and the current batch, not a persistent browser history or a complete historical job catalogue. Select a result, compare Result / Original / Side by side, review the six categories, then explicitly Save. Images remain uncropped; narrow screens use document flow and list/image/evaluation anchors. Resizing or changing theme preserves the same editor, selection and draft.

Historical comparison uses the owner-only GET `/tools/api/jobs/{requestId}/captured-source` after the sealed result has been read. It returns the retained generation-time original PNG and captured identity, bound to the same owner/job/batch/item/snapshot. The client verifies that binding, the original image SHA and image decoding before displaying it. It never substitutes the live Wiki image or current generation selector for a historical original. An unavailable original can be explicitly checked again while verified result review continues; mismatched source evidence is refused.

Evaluation drafts stay only in browser memory, keyed to the current session epoch, owner, job and PNG SHA, with the full result binding checked before saving. Changing result, task or generation context with unsaved edits offers Continue (the default, also Escape), Keep draft and move, or Discard edits and move. Returning to a kept draft revalidates its result; it cannot supply another result's payload. Discard resets editable content, not an in-flight or uncertain save attempt. Reload, logout or authentication loss clears these drafts; there is no durable browser recovery. Deliberate logout offers Continue or Discard and end session, not Keep.

Save captures an immutable evaluation ID, expected revision and exact payload. A lost or uncertain response blocks new submissions for that draft; the explicit retry control resends that same request, never a new ID or changed content. Verified history resolves the attempt only when its complete binding, content and revision transition match. Late responses reconcile the originating result even after navigation. Newer server revisions and CAS conflicts preserve edits and require checking the refreshed history followed by another explicit Save; they do not silently overwrite or automatically resubmit. Human verdict remains separate from candidate HOLD, machine NOT_RUN and approval NONE.

Single production selects a registered original or uploaded sheet, shows the source and required conditions, and sends one candidate only on the explicit Generate action. Batch composition has an independent selection: select eligible people across pages, inspect the frozen identities/source hashes, remove unwanted entries, confirm names and count, then explicitly submit. The maximum is 20 distinct people including pending selection reads. Selection changes or removals invalidate confirmation; stale hashes are rejected rather than silently replaced. Switching tasks, comparing images, resizing and reading status never submit generation requests.

Execution status opens after a batch response or explicit status lookup confirms server acceptance. A provisional submission ID with a lost response is not an accepted queue: use that ID for status lookup only, with no automatic replay. Accepted items retain server ordinal order and sequential dispatch. UNKNOWN is not confirmed completion and pauses later dispatch while preserving owner uncertainty; a new UUID or connection cannot bypass it. Execution FAILED, machine diagnostics and human verdict are distinct. Cancel pending cancels only undispatched PENDING items; RUNNING or uncertain work and consumed cost are not claimed cancelled.

GET /tools/api/wiki/people?q=&limit=25&cursor=0 queries the actual live published Wiki, discovering its current HTML index and peopleCatalog asset rather than listing the six SQLite originals. GET /tools/api/wiki/people/person-1003 retrieves the actual published person-details JSON. WIKI_BASE_URL defaults to https://seoul-dengoku.linalab.io/wiki/; only that production origin or explicit loopback fixture origins are accepted, always under /wiki/. Requests are bounded to 10 seconds and 2 MiB, reject redirects, and parse catalogue literals with the repository's existing Babel parser version without executing remote JavaScript. No stale SQLite fallback is used. Source URL, exact byte hash and fetch time distinguish live Wiki data from immutable original generation references. Query endpoints retain GitHub session protection. A selected person can generate only when original personId/characterId/name match the existing source-bound token/image tuple; missing references and identity drift are explicit eligibility failures.

An UNKNOWN job, or a persisted RUNNING job from an interrupted dispatch, holds every new UUID generation for that GitHub owner with OWNER_DISPATCH_UNCERTAIN. The explicit, evidence-preserving terminal-rejection v1 operation below is the only recovery exception. A complete, definitively captured invalid response remains FAILED, not UNKNOWN.

### Explicit terminal rejection v1

`POST /tools/api/v1/jobs/{requestId}/terminal-rejections` requires the existing signed owner session, exact Origin and session X-CSRF-Token. Its strict JSON body is `{schemaVersion:1, operationId, expectedJobSHA256, expectedPayloadSHA256, expectedReceiptSHA256, expectedRequestSHA256, expectedResponseSHA256, expectedRetainedManifest}`. The operation ID is a UUID scoped to this owner/job; each SHA-256 is lowercase hex over the exact retained file bytes, including JSON whitespace/newlines. The five hashes respectively identify `job.json`, `request-payload.json`, `provider-source.png.receipt.json`, `provider-source.png.request.bin`, and `provider-source.png.response.bin`. The payload hash here is the file hash, not the canonical `job.payloadSHA`. No path, replacement state, image, model claim, provider body, or owner ID is accepted from the caller.

The sole storage-owning server takes its existing owner admission exclusion. `commitTerminalRejectionV1` in `src/terminal-rejections.ts` reads safe, nonsymlink owner-private files and calls `verifyTerminalRejectionV1` in `src/terminal-rejection-proof.ts`. Only an original UNKNOWN/LOCAL_MODEL_NOT_EXPOSED single schemaVersion 2 reference-img2img OpenAI-compatible job is eligible. Its initial job, canonical payload, retained connection owner/identity, request record, multipart wire, receipt, and complete UTF-8 JSON response must agree. The receipt must report completed numeric 2xx, MODEL_NOT_EXPOSED and UNKNOWN model attestation; the raw response must independently omit a returned model. Network loss, partial/invalid bodies, other providers/modes, batch membership (including missing-marker membership), candidates, results, evaluations, stale hashes and mismatched proof are rejected. The retained connection need not remain live: this operation never dispatches to it.

The only committed artifact is `jobs/{requestId}/terminal-rejection.v1.json`: an immutable versioned event binding owner/actor, operation request, timestamp, all fourteen retained-file hashes, and the exact FAILED after-state. `job.json`, its initial history, raw transport files, modelAttestation UNKNOWN, and dispatch.lock remain unchanged. The server flushes a private staging file and atomically publishes it by exclusive hard link; on POSIX it synchronously flushes the job directory before yielding to readers. Windows uses the existing evaluation-store contract of flushed file plus exclusive hard-link publication because directory fsync is unavailable. This guarantees process-crash replay, not a claim about hardware/filesystem power-loss behavior. Staging leftovers from a process crash have no authority and are not interpreted as events.

The closed server-owned proof manifest requires `job.json`, `initial-job.json`, `request-payload.json`, `connection-binding.json`, `provider-source.png.request.json`, `provider-source.png.receipt.json`, `provider-source.png.request.bin`, `provider-source.png.response.bin`, `dispatch.lock`, `job-history.json`, `provenance.json`, `reference-analysis.json`, `reference-normalized.png`, and `source-bytes.json`. Every file must be present; the event binds its exact SHA-256. All fourteen are reread for the precommit CAS and checked against the event before every execution fold. Missing or changed proof returns 409 without publishing an event, or fails the committed fold and admission closed. The required `expectedRetainedManifest` maps exactly these fourteen fixed names to lowercase SHA-256 pins selected by the authenticated owner from a previously recorded and approved snapshot. Missing/extra/path keys, non-hashes, or an absent manifest are 422. Every current file must match its expected pin before semantic proof checking (409 on mismatch). The same manifest is retained in the operation request/event; changing any pin under the same operation ID conflicts. The five existing expected hashes must also match and cannot contradict the manifest. No caller-selected file list or paths are accepted.

Expected pins are owner-approved compare-and-swap inputs, not signatures, provider attestation, or a new remote trust service. The application worker must use the independently recorded fourteen-file hash snapshot in the reviewed application body; it must not regenerate expected pins from possibly changed files to make a conflict pass. Independently of these pins, recovery checks empty dispatch.lock, the history timestamp, provenance request/source hashes, canonical base64 retained sources, reference source selection, analysis record hashes/equality with transport provenance, manifest source/token bindings, directive request ID, and the retained normalized PNG hash against `transformReferencePng` of the retained original. Hash equality of a newly measured file alone is not pre-proof authority.

`readExecutionJobV1` folds the event for listing, history, inspection, individual job reads, generation replay, result eligibility, startup and owner admission. Retained history continues to display the original UNKNOWN bytes; inspection additionally includes the terminal event. The server rechecks the retained proof on every fold and fails closed if a committed event or its proof is damaged. The event changes execution to FAILED/LOCAL_MODEL_NOT_EXPOSED only; review remains HOLD, model attestation remains UNKNOWN, image adoption is NONE, and result/image routes stay unavailable. Other unresolved jobs and batches continue to block admission.

A newly committed operation returns 201 `{created:true,event,job}`. Exact replay returns 200 with the same event, including after a lost response or restart. Concurrent exact requests produce one event; a changed operation ID or hashes conflicts with 409 TERMINAL_REJECTION_CONFLICT. Invalid eligibility/proof returns 409 TERMINAL_REJECTION_INELIGIBLE or TERMINAL_REJECTION_PROOF_MISMATCH; active dispatch returns 409 JOB_RUNNING. Invalid input is 422, and normal authentication/CSRF/owner-private 401/403/404 behavior applies. Recovery never submits a provider request, retries generation, adopts or approves a PNG, or clears an owner-wide flag. Operators must run it through the sole owning server, never through an offline storage mutator or a second server over the same storage root.

POST /tools/api/generations requires an explicit live connectionId for each new synchronous one-candidate action. Missing authority returns CONNECTION_REQUIRED before Wiki, DNS or MCP calls. Foreign/missing connections return the same CONNECTION_NOT_FOUND. The route preserves canonical preparePortraitConditions/projectPortrait authority, pins the exact registry snapshot in an owner-private connection-binding.json sidecar, and invokes the fixed MCP tool through synchronous per-request registry dispatch authorization. The strict job wire schema remains unchanged. Terminal replay is local (including replay without connectionId); changed payload is REQUEST_CONFLICT. A single owner lease covers admission before its first async storage/source/network operation and remains held through terminalization. Persisted RUNNING/UNKNOWN holds new IDs and connections. Exact canonical projection, reference/request bytes, provenance, MCP request/response wire bytes, candidate PNG, returned receipt and machine diagnostics stay private. MCP wire is named mcp-response.bin with separate transport metadata, not falsely labelled upstream provider HTTP. Definitive correlated failures are FAILED, incomplete/uncertain dispatched outcomes are UNKNOWN, and validated candidates are HOLD. Files are exclusive-create and the terminal job is atomically renamed. No retry or automatic recovery occurs.

PNG decoding reuses the canonical acceptance decodePng API with portal byte/dimension/allocation bounds and the existing RGBA upload requirement. canvasOpaqueFraction is count(alpha >=250) / canvas pixels. The compatibility coreFraction field retains that same canvas calculation and explicitly declares coreFractionDenominator=canvasPixels. foregroundCoreFraction is count(alpha >=250) / count(alpha >0), matching the acceptance evaluator denominator; it is null for zero foreground. The alpha 250 cutoff comes from PORTRAIT_ACCEPTANCE_CRITERIA, not a copied threshold. These fractions, alpha-zero fraction, border occupancy and 32px margin occupancy are diagnostics only. mechanicalStatus=NOT_RUN means integrated acceptance/profile evaluation has not run. They do not establish anatomy, visual correctness or production approval. Every generated result is HOLD until a separately approved complete acceptance/profile bundle is available. No production approval endpoint is provided.

## People batches

Only one CONNECTING or READY connection may belong to a numeric owner across all signed sessions, except in explicitly configured personal server-provider mode described above. A second session cannot replace that connection or use its authority; it can connect after the first is disconnected, revoked or expired. The personal server-provider exception allows one connection per signed session, not shared session authority. Exact-session ownership remains required for every access and dispatch.

Cancel after COMPLETED is an exact no-op, including the cancellation flag and durable revision. Repeated cancel also makes no additional durable change. A pre-dispatch snapshot or read-resource block pauses as PAUSED_BLOCKED with unstarted items still PENDING; restoring the artifact and replaying the batch does not retry it. Losing session/connection authority or restarting cancels the remaining pending membership without resuming it.

POST /tools/api/batches strictly accepts {batchId,connectionId,providerModel,faceMode,items}. The client supplies one UUID batchId per deliberate submission. Model is gpt-image-2.5-sunburst and faceMode is {kind:"unique",variantId:null}. Each of 1..20 ordered, distinct selections contains personId, characterId, name, wikiDetailSHA and originalSourceHashes:{detail,token,image}; use the live Wiki detail SHA and non-null original hashes reported by generationEligibility. Extra fields, sheets, duplicates and stale selections are rejected. Auth, exact Origin/CSRF, owner uncertainty/active lease and the exact live session connection precede source network requests. Every selected source is preflighted before any image call; an invalid second selection rejects the entire batch without partial membership.

Admission returns 202 {batch} asynchronously. Exact payload replay under the same batchId returns 200 locally with unchanged server-created itemId/requestId UUIDs; changed payload returns REQUEST_CONFLICT. GET /tools/api/batches/{batchId} is an owner-private local read. POST /tools/api/batches/{batchId}/cancel-pending accepts only {} and cancels only undispatched PENDING items. In-flight work remains RUNNING until its actual outcome; cancellation does not claim consumed work or cost was cancelled. A running batch retains the same numeric-owner lease as single generation and connection handshakes for the entire sequence. Definite FAILED items continue once without retry; UNKNOWN pauses remaining work and keeps the durable owner uncertainty lock across new UUIDs and sessions.

Batch states are RUNNING, PAUSED_UNKNOWN, PAUSED_RESTART, PAUSED_BLOCKED, CANCEL_REQUESTED, COMPLETED and CANCELLED. Item status is PENDING, RUNNING, HOLD, FAILED, UNKNOWN or CANCELLED. HOLD is a candidate, not approval. Disconnect, logout, expiry and restart stop undispatched work while retaining known PNGs, receipts, terminal results and uncertainty. Restart never schedules an old batch, and there is no resume or substitution route. One service process must own a storage root.

The server atomically publishes owner-private batches/{batchId}/batch.json only after immutable items/{itemId}/snapshot.json and SHA-addressed artifacts/{sha256}.bin are written. Shared exact template artifacts are stored once per batch. Snapshot SHA hashes exact manifest bytes including its newline and binds source/Wiki bytes, identity, derived projection, pins and nonsecret connection/session/tool authority. jobs/{requestId}/batch-binding.json is only a server-written locator. resolveBatchBinding({ownerRoot,ownerId},requestId) in src/batches.ts reads the existing record and exact snapshots/artifacts and verifies membership and hashes; it never trusts client binding fields or initiates network requests. Completed batch items retain the existing strict job schema and owner-private image routes.

Batch admission reserves exact unique immutable snapshot/artifact bytes and the exact derived request/source/projection copies that each job retains, plus 25 MiB per item for retained output. The 25 MiB allowance covers the 12 MiB bounded raw MCP response, 8 MiB candidate PNG, up to 4 MiB UTF-8 receipt (the protocol caps UTF-16 string length at 1,048,576), and 1 MiB for job/diagnostic/record growth. This is retained evidence across all completed items, not parallel working buffers; only one image call runs at a time. The whole-store cap stays 512 MiB by default. A 20-item submission needs at least 500 MiB plus exact sources/requests/snapshots and existing usage, so the 20-item shape limit does not promise admission at default capacity. STORAGE_LIMIT rejects the entire batch before any image call; reservations are released in finally and persistent files remain counted in store usage.

## Result evaluation HTTP contract

All three routes require the existing verified signed session. POST also requires the exact configured public Origin and session X-CSRF-Token before parsing its bounded JSON body. Owner storage and reviewer identity come only from the numeric session ID. Each call uses src/evaluations.ts to reverify exact PNG, receipt, machine diagnostics, source snapshot and actual admitted batch membership locally, without Wiki or MCP calls. Responses use no-store and fixed error codes; no raw request, receipt transport, source or credential download route is exposed.

- GET /tools/api/jobs/{requestId}/result returns 200 {result}, where result is portal-generated-result.v1 with ownerId, jobId, batchId/itemId (null for a single job), snapshotSHA, pngSHA, receiptSHA, imageUrl, machineEvidence, reviewStatus:"HOLD" and approval:"NONE". It may idempotently seal an existing complete HOLD candidate on first access; repeated reads retain its original measuredAt. No missing evidence is regenerated.
- GET /tools/api/jobs/{requestId}/evaluations returns 200 {resultBinding,machineEvidence,latest,history}. latest is null and history is [] before the first review. This read requires an already sealed result; call GET result first. Machine evidence remains separate from human evaluations.
- POST /tools/api/jobs/{requestId}/evaluations accepts only {evaluationId,expectedRevision,pngSHA,receiptSHA,machineMetricsSHA,verdict,categories,notes}. It returns 201 {evaluation} for a new append and 200 {evaluation} for an identical evaluationId/payload replay, even if that replay's expectedRevision is now stale. A changed payload with the same ID is 409 REQUEST_CONFLICT. New IDs with stale expectedRevision are 409 EVALUATION_REVISION_CONFLICT. The server supplies reviewerId, reviewedAt, revision and previousRevision.

Review SHA values are 64 lowercase hexadecimal characters and must equal result.pngSHA, result.receiptSHA and result.machineEvidence.metricsSHA. expectedRevision is a nonnegative safe integer (less than Number.MAX_SAFE_INTEGER). verdict and each category judgement are pass, needs-change or hold. categories strictly contains identity-and-face, anatomy-and-pose, framing-and-composition, technique-and-style, transparency-and-edges and authored-conditions, each with {judgement,notes}. Category notes allow at most 2000 Unicode characters and overall notes at most 8000. Overall pass requires all categories pass; needs-change requires a needs-change category with nonblank notes; otherwise the overall verdict is hold. Extra client owner, reviewer, timestamp, revision, binding, approval, metrics, path or connection fields are 422 INVALID_INPUT. Malformed JSON is also INVALID_INPUT and the existing 12 MiB body cap applies.

Missing and foreign owner jobs are indistinguishable 404 NOT_FOUND. Non-HOLD or incomplete candidates return 409 RESULT_NOT_AVAILABLE. Changed exact PNG bytes return RESULT_HASH_MISMATCH; changed receipt/diagnostic evidence returns RESULT_EVIDENCE_MISMATCH; changed batch/source binding returns SOURCE_SNAPSHOT_MISMATCH, all 409. Human pass never changes job HOLD, mechanical NOT_RUN or approval NONE. Existing GET job and private GET image retain their strict wire shapes.

The batch read contract intentionally joins evaluation details client-side: GET /tools/api/batches/{batchId} retains {batch} and its item.requestId/status/job fields, without embedding result/evaluation sidecars or rehashing every result on each progress read. For each HOLD item, fetch GET /tools/api/jobs/{item.requestId}/result followed by GET /tools/api/jobs/{item.requestId}/evaluations; display latest.revision/verdict as that item's human evaluation summary. Refresh that item's history after a review or CAS conflict. This makes summaries current through the verified per-item APIs without new dispatch or mass hashing. Exact real HTTP JSON fixtures and check receipts are in .omo/evidence/portal-20261013/evaluation-routes-implementation.json at the repository root.

```sh
node /absolute/path/to/dist/server.mjs
```
