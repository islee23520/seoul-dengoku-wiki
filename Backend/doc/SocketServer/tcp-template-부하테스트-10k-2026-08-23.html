3이번 테스트를 위한 코드 변경

Echo 패킷에 문자열 필드를 추가했습니다. 문자열 처리 비용을 측정에 포함시키기 위한 변경입니다.

패킷 형식

ReqEcho        [nData int32][Length int32][Message UTF-8 Length바이트]
ReqEchoResult  [DummyIdx int32][Length int32][Message UTF-8 Length바이트]

Message = "Y2K-ECHO-{Idx:D6}-0123456789ABC...XYZ" 를 100자로 맞춘 문자열 (클라이언트마다 다름)

본문은 리틀 엔디안 고정입니다. IsBigEndian은 헤더에만 적용되는 규약을 그대로 따랐습니다.

RTT 측정 방식

송신 직전 Stopwatch 틱을 기록하고 응답 처리 시점에 소비하는 방식입니다. Interlocked.Exchange로 값을 소비하므로 응답 1건이 송신 1건에만 대응하고, 짝이 맞지 않으면 평균에 넣지 않고 unmeasured로 따로 셉니다. 이번 테스트에서 unmeasured는 0이므로 모든 표본이 정상적으로 짝지어졌습니다.

7해석 — 지연은 어디에서 왔나

미니(Gemini) 크로스체크를 거친 분석입니다. 확인된 사실과 추정을 구분해 적었습니다.

확인된 사실

  • 서버 CPU는 평균 3.6%, 최대 10.1%입니다. 연산 포화는 아닙니다.
  • 최소 RTT 91.3us는 경합이 없을 때 이 경로가 그만큼 빠르다는 뜻입니다.
  • 손실·에러·불일치가 0이므로 지연은 있어도 유실이나 순서 붕괴로 이어지지 않았습니다.
  • 클라이언트 프로세스가 서버와 거의 같은 CPU를 소비했습니다 (클라 0.95 core vs 서버 0.81 core).

지연의 주된 출처 — 서버 밖

측정한 RTT는 클라이언트가 송신하기 직전부터 클라이언트가 응답을 처리하는 시점까지입니다. 이 구간에는 서버 처리 시간 외에 다음이 모두 포함됩니다.

요인설명구분
클라이언트 수신 큐 대기클라이언트 한 프로세스가 10,000 세션의 응답을 ThreadPool로 처리합니다. 응답이 몰리면 처리 순서를 기다리는 시간이 그대로 RTT에 들어갑니다.추정
서버·클라 CPU 경합같은 PC에서 두 프로세스가 CPU·캐시·스케줄러를 공유합니다. 합산 1.76 core를 두 프로세스가 번갈아 점유합니다.사실
클라이언트 GCGen0 485회 / Gen1 335회 / Gen2 98회. Gen2가 98회면 무시할 수 없는 정지 시간입니다.사실
송신 동시 몰림스폰이 10초에 분산됐으므로 매 순간 약 1,000개가 동시에 송신합니다. 순간 부하는 평균의 약 10배입니다.추정
그래서 이 RTT는 서버 지연 지표가 아닙니다 서버만의 처리 시간을 재려면 서버 안에서 "수신 완료 → 응답 송신 완료" 구간을 직접 측정해야 합니다. 현재 PerfStats는 BulkEcho에만 처리 시간 계측이 있고 Echo에는 없습니다. 이번 리포트의 RTT는 시스템 전체의 왕복 시간으로만 읽어야 합니다.

이 테스트로 말할 수 있는 것 / 없는 것

말할 수 있는 것아직 말할 수 없는 것
  • 10,000 동시 세션을 5분간 유실 없이 유지한다
  • 3백만 건 왕복에서 세션 라우팅이 한 번도 어긋나지 않는다
  • 세션 수에 스레드가 비례하지 않는다 (10,000 세션 / 41 스레드)
  • 세션당 메모리 약 46KB로 예측 가능하다
  • 이 부하에서 서버 CPU 여유가 크다 (3.6%)
  • 서버 자체 지연 — 클라·OS 오버헤드와 분리되지 않음
  • 최대 처리량 — CPU가 포화되지 않아 한계를 못 봄
  • 실제 네트워크 성능 — loopback이라 NIC·드라이버 미검증
  • 실 컨텐츠 부하 — DB·Redis I/O가 붙은 처리기는 미검증
  • 장시간 안정성 — 5분으로는 누수 판단 불가

8다음 단계 제안

우선순위 순입니다. 실행 여부는 지시를 기다립니다.

#항목내용
1 서버 자체 지연 계측 추가 PerfStats에 Echo 처리 시간 계측을 넣습니다 (BulkEcho에는 이미 있음). 수신 완료 → 응답 송신 완료 구간을 서버가 직접 재면 클라·OS 오버헤드와 분리됩니다. 변경량이 가장 작고 효과가 큽니다.
2 부하 생성기 분리 클라이언트를 여러 프로세스로 쪼개거나 다른 장비(맥미니 등)에서 돌립니다. 현재 클라이언트가 서버와 맞먹는 CPU를 쓰고 있어 이것만으로 RTT 해석이 크게 달라집니다.
3 한계점 탐색 송신 주기를 1초에서 100ms·50ms로 줄여 CPU가 포화되는 지점을 찾습니다. 현재는 서버 여유가 커서 한계가 드러나지 않았습니다.
4 장시간 유지 테스트 같은 조건으로 1시간 이상 돌려 메모리·핸들 증가 추세를 봅니다. 5분으로는 누수를 판단할 수 없습니다.
5 수신 파이프 상한 확인 기존에 파악된 RecvPipe 실효 상한(약 64KB) 이슈는 이번 테스트(116B 패킷)에서는 건드리지 않았습니다. 큰 패킷 시나리오는 별도 검증이 필요합니다.
