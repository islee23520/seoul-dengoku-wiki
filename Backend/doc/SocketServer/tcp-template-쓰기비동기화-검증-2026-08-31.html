결론 — 현행 동기 쓰기 유지 (미채택)

기술적으로는 가능하고 정확성도 동일하지만, 고동시성에서 현행보다 나쁘고 손실까지 발생한다. 현행 동기 구조의 안정성이 비동기 전환의 이득보다 크다고 판단해 채택하지 않는다. 읽기(SELECT) 비동기는 별개이며 이 문서의 범위가 아니다.

1. 배경

쓰기 경로를 동기로 강제한 결정의 근거는 키 취득–후속삽입 순서 의존성이었다.

UPDATE 자체는 비동기로 처리해도 무방하다. 그러나 DBConnector.Attach 로 쌓인 엔티티 목록에는 Insert 와 Update 가 함께 존재할 수 있고, Insert 로 생성된 auto increment key 를 후속 Update 가 다른 테이블에 써야 하는 경우가 있다. 이 순서 의존성 때문에 개별 연산이 아니라 쓰기 배치 전체를 동기로 묶는다. — 팀장, 2026-08-31

다만 코드를 읽어보면 RunDbCommandAsync 는 foreach 안에서 await 하므로 순서 자체는 비동기에서도 유지된다(DBConnector.cs:156-174). 그렇다면 실제 제약은 순서가 아니라 auto-key 취득 API가 아닌가 — 이 가설을 검증하기 위해 예제 프로젝트를 만들어 실측했다.

2. 검증 방법

항목내용

참조Y2K.Core.DataBase.dll + Dapper 2.1 + Dapper.Contrib 2.0 + MySqlConnector 2.3 — DB.csproj 와 동일 버전
대상 DB맥미니 MySQL 9.6.0. 실제 게임 DB 를 건드리지 않도록 별도 임시 테이블 사용, 종료 시 삭제
연결 옵션프로덕션 GAME_DB(global_db.tbl_connection_info) 옵션을 그대로 본뜸
비교 대상① 현행 동기(Contrib Insert) ② 비동기 2왕복(ExecuteAsync + SELECT LAST_INSERT_ID()) ③ 비동기 1왕복(두 문장을 한 번에)

실제 사용 패턴을 그대로 본떴다 — 도메인 객체가 PrimaryKeyCallback 을 구독하고, 엔티티 Insert 가 실행되면 그 콜백으로 키를 되돌려받는다. 자식 엔티티는 실행 시점에 부모 도메인 객체에서 키를 읽는다. 템플릿의 Energy / Hero 구조와 동일하다.

3. 정확성 — 동기와 비동기가 동일하다

14개 판정 전부 통과.

케이스검증 내용결과
1동기 기준선 — auto-key 전파, 자식이 그 키를 저장통과
2비동기 — ExecuteAsync + LAST_INSERT_ID() 로 동기와 동일한 결과통과
3a동기 + 트랜잭션 (템플릿 현행 조건)통과
3b비동기 + 트랜잭션통과
3d자식 Update 실패 시 부모 Insert 롤백통과
4LAST_INSERT_ID() 세션 종속 — 같은 커넥션 유효, 다른 커넥션은 0통과
5반례 — auto_increment 없는 테이블에서 예외 아닌 0 반환통과
6실행 순서 — Attach 순서대로 auto-key 증가통과
가설은 맞았다. 순서는 비동기에서도 유지되고, 같은 커넥션에서 순차 await 하면 auto-key 취득과 콜백 전파가 동기와 완전히 같다. 즉 정확성은 비동기 전환의 장애물이 아니다.

비동기로 바꾸는 것만으로는 빨라지지 않는다. 왕복 횟수가 같기 때문이다(오히려 상태머신 오버헤드로 1.4% 느림). 이득은 비동기가 열어주는 왕복 축소에서 나온다 — INSERT ...; SELECT LAST_INSERT_ID(); 를 한 번에 보내 행당 왕복을 2회에서 1회로 줄이면 절반 가까이 빨라진다.

5. 동시 세션 부하 — 여기서 갈린다

6. 원인 — 사라진 제동장치

예외가 터진 위치가 원인을 정확히 가리킨다.

MySqlConnector.MySqlException: Connect Timeout expired. All pooled connections are in use.
   at MySqlConnector.MySqlConnection.Open()
   at Y2K.Core.DataBase.DBConnector`1..ctor(String connectionString, Boolean useTransaction)
      in DBConnector.cs:line 31

DBConnector 는 생성자에서 Connection.Open() 을 동기로 호출한다(DBConnector.cs:30-38). OpenAsync 경로가 없다. 따라서 쓰기 본문을 비동기로 바꿔도 커넥션 획득 구간은 여전히 스레드를 블로킹하고, 풀이 고갈되면 그 자리에서 예외를 던진다.

동기 경로에서는 스레드풀(32~34개)이 사실상 admission control 로 작동한다. 의도된 설계는 아니지만 결과적으로 커넥션 풀을 고갈시키지 않는다. 비동기는 그 제동이 사라져 하류(커넥션 풀)를 그대로 때린다. 이것이 256 세션에서 역전이 일어난 이유다.

8. 부수 발견 — IgnoreCommandTransaction

검증 중 별개의 사실을 확인했다. 앞으로 같은 함정에 걸리지 않도록 남긴다.

DBConnector 는 _transaction 을 private 로만 갖고 IY2KDbConnector 에도 접근자가 없다(Interface.cs:38-51). 따라서 엔티티가 Dapper 를 호출할 때 command.Transaction 을 지정할 방법이 없고, MySqlConnector 는 이 경우 예외를 던진다.

위치옵션
global_db.tbl_connection_info 의 GAME_DBIgnoreCommandTransaction=true 있음 → 트랜잭션 쓰기가 정상 동작
appsettings.json 의 GlobalDB없음
게임 DB 연결문자열은 appsettings.json 이 아니라 DB 테이블에서 온다(DBConfig.Init). 이 옵션은 비동기 때문에 새로 필요한 것이 아니라 현행 동기 경로도 이미 의존하고 있는 조건이다. appsettings 만 보고 "옵션이 없다" 고 판단하면 오진한다.

9. 측정하지 않은 것

  • 1,000,000건 순차 측정 — 실측 74건/초 기준 3방식 합계 약 9시간 35분으로 판단돼 동시 세션 측정으로 대체했다. 순차 측정은 동기/비동기 차이를 구조적으로 드러내지 못한다(위 4장에서 1.4%로 확인).
  • 읽기(SELECT) 비동기화 — 이 문서의 범위가 아니다. 별도 논점으로 남아 있다.
  • 실제 게임 DB 대상 측정 — 프로덕션 데이터를 건드리지 않기 위해 별도 임시 테이블을 사용했다. 스키마·부하 특성이 실제와 다를 수 있다.
