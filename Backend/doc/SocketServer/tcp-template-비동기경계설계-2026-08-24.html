3. 설계 판단 3건과 그 근거

판단 ① 비동기 계약이 필요한 것은 DB 스토리지 5개다

근거(측정). Cache 스토리지의 GetData는 Redis를 부르지 않는다. Redis 왕복은 CacheDataProvider가 먼저 끝내고 param.SourceData에 담아 둔다(CacheDataProvider.cs:154). 스토리지는 그 딕셔너리를 역직렬화한다.

// AccountCacheStorage.cs:17-35 — 메모리 작업만 한다
string cacheKey = MetaClass.GetCacheMetaData(param.Key).Key;
if (param.SourceData.ContainsKey(cacheKey) == false || param.SourceData[cacheKey] == null)
    return null;
var result = JsonSerializer.Deserialize<Account>((string)param.SourceData[cacheKey]);

// HeroInventoryDbStorage.cs:21-41 — 실제 쿼리를 친다
var entities = HeroEntity.LoadFromDB(db.Connection, param.AuthInfo.UID);

선택. IDataStorage를 통째로 바꾸지 않고 비동기 계약을 별도 인터페이스로 신설해 DB 5개만 구현한다. 전환 대상이 10개 → 5개가 된다.

대안과 비교. IDataStorage 자체에 GetDataAsync를 추가하면 Cache 5개도 구현해야 하는데, 그 구현은 동기 코드를 ValueTask로 감싼 형태가 된다. 지금 DbDataProvider가 가진 것과 같은 모양이 5개 더 생긴다.

판단 ② 원본 무수정으로 비동기 연결이 가능하다

제약. DBConnector<T>는 생성자에서 동기로 연결을 연다. 생성자는 await를 못 하므로 파생 클래스로는 바꿀 수 없다. 그리고 Y2K.Core는 수정 금지다.

근거(측정). DataBaseStorageParameter.DbConnector의 타입이 구체 클래스가 아니라 인터페이스다.

// Y2K\.core\source\DataBase\Interface.cs:38-49
public interface IY2KDbConnector : IDisposable
{
    IDbConnection Connection { get; set; }
    List<Entity> AttachEntities { get; }
    void Attach<T>(T entity) where T : Entity;
    void AttachList<T>(T entities) where T : IEnumerable<Entity>;
    void Commit();
    ValueTask CommitAsync();
}

// Storage\Interface.cs:72
public IY2KDbConnector DbConnector { get; set; }

선택. tcp_template 안에 IY2KDbConnector + IAsyncDisposable을 독립 구현한 비동기 커넥터를 만들어 끼운다. 상속이 아니라 같은 계약을 따로 구현하는 방식이며, 2026-08-22에 네트워크 계층에서 채택한 방식과 같다. 원본 수정 0바이트이므로 별도 승인이 필요 없다.

public sealed class GameDbAsyncConnector : IY2KDbConnector, IAsyncDisposable
{
    // 생성자에서 열지 않는다. 정적 팩토리에서 비동기로 연다.
    public static async ValueTask<GameDbAsyncConnector> CreateAsync(string connectionString, bool useTransaction = false)
    {
        var conn = new MySqlConnection(connectionString);
        await conn.OpenAsync().ConfigureAwait(false);

        DbTransaction tx = null;
        if (useTransaction == true)
        {
            tx = await conn.BeginTransactionAsync().ConfigureAwait(false);
        }

        return new GameDbAsyncConnector(conn, tx);
    }

    // 원본과 같은 규약: Attach 로 쌓고 여기서 순서대로 일괄 실행한 뒤 커밋한다.
    public async ValueTask DisposeAsync() { ... }
}

IY2KDbConnector는 IAsyncDisposable을 포함하지 않으므로, 이 커넥터를 받는 쪽은 await using으로 받는다. 기존 동기 GameDBConnector는 그대로 두고 병행한다.

판단 ③ 아래층부터 전환한다

위층을 먼저 비동기로 바꾸면 아래가 동기라서 Task.FromResult 형태의 래핑이 다시 생긴다. 지금 DbDataProvider.GetDataAsync가 그렇게 만들어진 상태다. 따라서 스토리지 → 엔티티 → 제공자 → 파사드 → 처리기 순서로 올라간다.
